# GlossaryBuilder 仕様書

本仕様書は、ユビキタス言語辞書を作るモジュール `GlossaryBuilder` が果たすべき**責務の境界、取り扱う情報の定義、および守るべき契約（事前・事後・不変条件）**を定義する。
本仕様書はプロダクトマネージャー（PdM）やステークホルダーがシステムの振る舞いとして読解・合意可能な形式で記述され、プログラミング言語固有の内部コードには依存しない。

---

## 1. 責務の境界 (Responsibilities & Scope)

### 1.1 担当すること (In Scope)
- **ユビキタス言語辞書（`Glossary`）の作成（`BuildGlossary`）**:
  - `CommandExtractor` が作った全体マップの要素と、リポジトリから機械的に拾える実装の名前を、辞書の項目として載せる。各項目は、実装の名前と所在（ファイルと処理の名前）を持つ。
  - 辞書は、利用者向けの表示と実装との対応表（トレース）の正である。利用者向けの出力から実装の名前を外し、開発者（Eng）向けの表示では辞書を引いて実装の名前を併記する（全体設計の表示の役割）。
- **地図の要素への用語付け**:
  - 地図の要素（Bounded Context・コマンド・ドメインイベント・ポリシー）に、業務の言葉で用語を付ける。用語は LLM が付ける。
  - 用語を付けるとき、その要素に関係する仕様の資料の記述を手がかりにする。コードの関数名ではなく、資料に書かれた業務の言葉で用語を付けるためである。
- **用語を Bounded Context に所属させる**:
  - 用語は、それを付けた地図の要素が属する Bounded Context に所属する。Bounded Context が違えば、同じ言葉が別の意味になりうるためである（DDD のユビキタス言語は Bounded Context ごとに定まる）。
  - Bounded Context をまたぐポリシー（あるコンテキストのイベントが、別のコンテキストのコマンドを起動するもの）は、両方の Bounded Context に関わることを記録する。現在の範囲では、1 つの項目は 1 つの用語だけを持ち、Bounded Context ごとに別の呼び名を持たない。
- **用語の意味として、資料の節の抜粋を持つ**:
  - 用語の出どころにした資料の節の本文から、抜粋を機械的に切り出して項目に持つ。画面はこの抜粋を、その用語の意味として見せる（SpecViewer 仕様 2.2）。画面が資料を読み直さずに済むようにするためである。
  - 資料に記述が無い要素は、抜粋を持たない。LLM に意味の文を書かせることは、現在の範囲に入らない（1.2）。
- **確定の状態を記録する**: 用語と意味（抜粋）は、確定の状態（未生成・候補・確定・要再確認。SpecViewer 仕様 2.4）を持つ。本モジュールが作った用語と抜粋は、人が確かめるまで「候補」である。
- **資料とコードのずれの記録**:
  - どの資料にも記述が見つからない地図の要素と、資料に出てくるのにどの項目にも対応しない名前を記録する。記録して見せるだけで、どちらかに合わせて直すことはしない。
- 用語の所属、意味の抜粋、確定の状態、同義の数え方（2.2）は、2026-10-31 に画面の仕様（`spec_viewer.spec.md`）と合わせて足した（中瀬古様 C0AF4DJJK8A 1793383559.640939・1793384098.424799）。

### 1.2 扱わないこと (Out of Scope / 禁止事項)
- **地図の構造の変更**: 全体マップの要素を足す・消す・まとめる・分けることはしない。同じ用語が複数の要素に当たる場合（同義）や、1 つの要素に資料の言葉が複数ある場合も、記録して見せるだけで、要素をまとめない。意味に基づいて構造を変える判断は、インタラクションビューアー（全体設計を参照）で利用者が行う。
- **意図の候補**: Bounded Context とシナリオの意図の候補は作らない（`IntentSynthesizer` の責務）。
- **地図の要素以外への用語付け**: 地図の要素以外の項目（スキーマの項目、書き込み先など）は、実装の名前と所在だけを載せ、用語を付けない。利用者にも提示しない。
- **後段のモジュールが見つける名前の追記**: 状態の変数や条件のように、後段のモジュール（`ContextExtractor`・`FormalTranspiler`）が見つける名前は、辞書に追記しない。後段は、辞書の実装の名前と一致するものだけを引いて使う。辞書は 1 回の実行の途中で変わらない。
- **意味の文の生成**: 資料に記述が無い要素に、LLM で意味の文を書かせることはしない。
- **確定の操作**: 候補を確定にする操作は、現在の範囲に入らない。本モジュールが自分で項目を「確定」にすることはない。
- **資料とリポジトリの改変**: 資料もコードも書き換えない。

## 2. 取り扱う情報の定義 (Information Model)

### 2.1 入力情報 (Inputs)
| 入力情報 | 内容 | 必須/任意 |
| :--- | :--- | :--- |
| **全体マップ (`EventStormingMap`)** | `CommandExtractor` の出力 1 | 必須 |
| **リポジトリの中身 (`RepositoryArtifacts`)** | コードのファイルと、仕様の資料（README、`docs/` の Markdown、スキーマ定義）。集め方と上限は `CommandExtractor` の設計書 4.0 に定める | 必須（資料が無いリポジトリでは、資料が無いことを記録して先へ進む） |

### 2.2 出力情報 (Outputs)
- `BuildGlossary(map, repo) -> Glossary`: 辞書を作る。

#### 辞書 (`Glossary`)
- **項目 (Entries)**: 1 項目は次のものを持つ。
  - **項目の識別子**: 実装から機械的に決まる値から作る。地図の要素の項目は、その要素の識別子を使う。
  - **種類**: Bounded Context・コマンド・ドメインイベント・ポリシー（以上が地図の要素）と、それ以外の実装の名前の種類（スキーマのエンティティと項目、DB の書き込み先など。種類の一覧は設計書に定める）。
  - **提示の範囲**: 利用者と LLM が読む項目（地図の要素）か、記録だけの項目か。
  - **所属の Bounded Context**: 地図の要素の項目だけが持つ。全体マップの要素の所属をそのまま写す。Bounded Context の項目は自分自身を指す。
  - **またいでいる先**: Bounded Context をまたぐポリシーの項目だけが持つ。起動するコマンドが属する Bounded Context。
  - **用語**: 地図の要素の項目だけが持つ。LLM が付けた業務の言葉と、その確定の状態。付けられなかったときは「未生成」とその理由を持つ。
  - **実装の名前と所在**: 実装の名前（関数名、コレクション名など）と、ファイルと行。
  - **用語の出どころ**: 用語の手がかりにした資料の節（資料のパスと見出し）。資料を使わなかったときは無い。
  - **意味（資料の抜粋）**: 用語の出どころの節の本文の抜粋と、その確定の状態。抜粋の切り出し方と長さの上限は設計書に定める。出どころが無いときは無い。
- **資料とコードのずれ (Gaps)**:
  - **資料に記述が無い要素**: どの資料の節にも手がかりが見つからなかった地図の要素。
  - **項目に対応しない資料の名前**: 資料のコードの囲みや見出しに出てくる名前のうち、どの項目の実装の名前とも一致しないもの。
  - **同義と多義の候補**: **同じ Bounded Context の中で**同じ用語が付いた複数の要素と、1 つの要素に当たった複数の資料の言葉。
  - **Bounded Context ごとに意味が違う言葉**: **違う Bounded Context で**同じ用語が付いた要素。DDD では正常なことなので、ずれとしては数えず、別の区分として記録する。
- **読んだ資料の記録**: 読んだ資料の一覧、上限で一部だけを読んだ資料、上限で読まなかった資料。
- **元にした入力**: 元にした全体マップと資料の内容を特定する値（ハッシュ）。後段は、これで辞書が古くないかを確かめる。

## 3. 契約仕様 (Design by Contract)

### 3.1 事前条件 (Preconditions)
- `CommandExtractor` が作った全体マップと、それを作ったときと同じリポジトリの中身が与えられていること。

### 3.2 事後条件 (Postconditions)
- **網羅性**: 全体マップのすべての Bounded Context・コマンド・ドメインイベント・ポリシーが、辞書にちょうど 1 項目ずつある。用語が未生成の項目も載せる。
- **対応の正しさ**: 各項目の実装の名前と所在は、全体マップまたはリポジトリのコードにあるものと一致する。LLM の出力から所在を作らない。
- **所属の正しさ**: 地図の要素の項目の所属の Bounded Context は、全体マップの要素の所属と一致する。
- **抜粋の正しさ**: 意味の抜粋は、用語の出どころの節の本文にある文字列そのものである。LLM の出力から抜粋を作らない。
- **確定の状態**: 本モジュールが作った用語と抜粋は「候補」、作れなかった用語は「未生成」として記録されている。
- **ずれの記録の完全性**: 資料に記述が無い要素と、項目に対応しない資料の名前は、漏れなく記録されている。資料が無いときは、すべての要素が「資料に記述が無い要素」になり、そのことが分かる形で記録されている。同義の候補と「Bounded Context ごとに意味が違う言葉」は、同じ用語の組を両方に重ねて記録しない。

### 3.3 不変条件 (Invariants)
- **構造を変えない**: 辞書は全体マップの構造（要素・つながり・所属・識別子）を変えない。辞書を作る前と後で、全体マップは同じである。
- **決定論性**: 同一の全体マップとリポジトリの中身に対して、辞書は同一である。資料の節の選び方、抜粋の切り出し方、ずれの記録は、機械的な照合で決める。LLM が付ける用語は、出力を記録して再利用することでこれを満たす。記録のキーには、手がかりに使った資料の抜粋を含める。資料が変われば用語を作り直し、資料が同じなら用語は同じである。
- **確定の外れ**: 確定の操作を足したあと（現在の範囲外）、確定した項目の抜粋または実装の所在が変わったときは、その項目を「要再確認」にする。抜粋が記録のキーに入っているので、変わったことは機械的に分かる。
- **未生成を埋めない**: LLM に届かないときは、用語を「未生成」として記録し、関数名などから機械的に作った言葉で埋めない。項目の識別子と実装の所在はコードから決まるので、用語が未生成でも後段の処理は進む。
- **資料はデータとして扱う**: 資料に書かれた文は、解析の対象となるデータである。資料の中に指示の形の文があっても、本モジュールへの指示として扱わない。LLM に渡すときも同じである。
- **非破壊性**: 解析対象のリポジトリやドキュメントを一切改変しないこと。
