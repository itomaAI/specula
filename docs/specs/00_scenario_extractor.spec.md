# ScenarioExtractor 仕様書

本仕様書は、シナリオ同定モジュール `ScenarioExtractor` が果たすべき**責務の境界、取り扱う情報の定義、および守るべき契約（事前・事後・不変条件）**を定義する。
本仕様書はプロダクトマネージャー（PdM）やステークホルダーがシステムの振る舞いとして読解・合意可能な形式で記述され、プログラミング言語固有の内部コードには依存しない。

---

## 1. 責務の境界 (Responsibilities & Scope)

### 1.1 担当すること (In Scope)
- **Loom 双対構造（プロジェクト／タスク）に基づく階層的ドメインモデルの構築**:
  - システム全体から個別シナリオに至る詳細化の過程を、Loom の基本構造である **「終わらない意図・文脈を持つ器（プロジェクト相当の Bounded Context）」** と **「終わる完了条件を持つ1本の仕事（タスク相当の個別シナリオ）」** の 2 つの器として体系化する。
  - 概念は Bounded Context → 全体マップ → 個別シナリオ の順に具象化される。本モジュールの処理はすべてこの具象化の向きに進む。
- **イベントストーミング（Event Storming）による全体マップの作成（`DiscoverSystemContext`）**:
  - システムのリポジトリ構造、ドキュメント、画面定義、コードエントリーポイントを精査し、ドメインの時系列・因果関係を表す**「全体マップ（Event Storming Map）」**を作る。
  - **Bounded Context（境界づけられたコンテキスト）の同定と階層表現**:
    - コンテキスト境界が同定または推測可能な場合、全体俯瞰図（Context Map）とコンテキスト別詳細図の 2 階層に区分して表現する。
    - 密結合等により境界の同定が困難な場合は、無理な推測による境界分割を排し、システム全体を**単一の Bounded Context（Monolithic Context）**として透過的に取り扱う。
  - あるコンテキストのイベントが別のコンテキストのコマンドを起動するポリシー（コンテキストをまたぐ因果関係）も、全体マップの要素として記録する。
- **個別シナリオの切り出し（`SliceScenarios`。基本操作の「置く」）**:
  - 全体マップから、個別のコマンド（Command）またはポリシー（Policy）を起点として、アクター・リードモデル（画面）を補完したアトミックな「個別シナリオ (`ScenarioTarget`)」を切り出す。
- **利用者が定義したシナリオの受け入れ**:
  - 自動抽出したシナリオ候補とは別の入力として、人間（PdM）が定義したシナリオ（起点・画面・目的）と、切り出す範囲の絞り込み条件を受け取る。
  - 利用者が定義したシナリオは、全体マップに起点が存在することを確かめたうえで正規化して出力する。出力には出どころ（`origin`）を付け、抽出したシナリオと区別できるようにする。

### 1.2 扱わないこと (Out of Scope / 禁止事項)
- **コードの詳細な構文解析・深掘り追跡**: 関数内部の AST トラバースや API ➔ DB の深掘り事実抽出は行わない（シナリオ境界の同定と切り出しに閉じる）。
- **形式仕様コードの生成**: 数学モデルや形式仕様言語への変換は行わない。
- **特定リポジトリの固定パスへの依存**: リポジトリ構造に固定的な決め打ちパスを仮定してはならない。
- **初回の実行での「畳む」「移す」**: 「畳む」（検証・合意された論点を親コンテキストの文脈へ還元する）と「移す」（確定したドメインイベントを別コンテキストへ伝播させる）は、検証と人間の合意の**後**に行う操作である。2 回目以降の実行で、前回の合意結果を本モジュールの入力として受け取って行う。初回の実行では行わない（全体仕様 1.5）。

## 2. 取り扱う情報の定義 (Information Model)

### 2.1 入力情報 (Inputs)
| 入力情報 | 内容 | 必須/任意 |
| :--- | :--- | :--- |
| **リポジトリ構造・見取り図情報** | リポジトリ構成、ルート定義、README、`docs/`、スキーマ定義 | 必須 |
| **画面一覧・UIメタデータ** | 利用可能な画面ルート、画面キャプチャ画像、主要コンポーネント | 任意 |
| **シナリオの選択 (`ScenarioSelection`)** | 絞り込み条件（`filter`）、利用者が定義したシナリオ（`userDefined`） | 任意（人間介入時） |
| **前回の合意結果** | 前回の実行で検証・合意された論点と不変条件（「畳む」の対象） | 2 回目以降の実行のみ。初回は無い |

### 2.2 出力情報 (Outputs)
本モジュールは、Loom の「プロジェクト（文脈）」と「タスク（仕事）」に対応する以下の 2 種類の成果物を出力する。公開する操作は 2 つに分ける。

- `DiscoverSystemContext(repo) -> EventStormingMap`: 全体マップを作る。
- `SliceScenarios(map, selection?) -> SliceResult`: 全体マップからシナリオ（`ScenarioTarget` の一覧）を切り出す。利用者が定義したシナリオもここで受け取る。起点が全体マップに無い利用者定義のシナリオは、出力せずに理由を付けて返す（`SliceResult` の `rejected`）。

#### 出力 1: イベントストーミング全体マップ (`EventStormingMap`) 【プロジェクト相当】
終わらない観点・意図・ドメイン知識の器。システム全体の因果連鎖を俯瞰する。
- **Bounded Contexts (境界づけられたコンテキスト)**:
  - **意図 (Intent)**: 当該コンテキストの業務ドメインにおける存在理由・責務
  - **文脈 (Context)**: コンテキスト内で生じる出来事の連鎖（ドメインイベントのタイムライン）
  - ※ 境界分離不可時はシステム全体を内包する `DEFAULT_CONTEXT`（単一コンテキスト）として定義。
- **イベントストーミング構成要素**:
  - **Domain Events (ドメインイベント)**: 発生した過去の確定事実（オレンジ付箋相当）
  - **Commands (コマンド)**: 意図・操作要求（青色付箋相当）
  - **Policies (ポリシー)**: 「イベント X 発生時、コマンド Y を起動する」反応ルール（藤色付箋相当）
  - **Read Models (リードモデル)**: コマンド決定のために参照される画面・ビュー（緑色付箋相当）
  - **Actors (アクター)**: 操作を実行する主体・役割（黄色小型付箋相当）
  - **Aggregates (アグリゲート)**: コマンドを受け入れイベントを発生させる状態エンティティ（黄色付箋相当）

#### 出力 2: 個別シナリオ同定情報 (`ScenarioTarget`) 【タスク相当】
単一の明確な完了条件を持つ、アトミックな1回の実行可能シナリオ。
- **シナリオ識別子 (`id`)**: 一意な識別ID（例: `SCN-RESET-PASSWORD`）
- **所属コンテキスト (`boundedContext`)**: 所属する Bounded Context ID
- **出どころ (`origin`)**: 全体マップから抽出したものは `EXTRACTED`、利用者が定義したものは `USER_DEFINED`
- **依頼・起点 (Inlet Trigger)**:
  - 起点種別: `COMMAND`（同期操作）または `POLICY`（非同期反応）
  - 起点名: コマンド名またはポリシールール
  - 起点の所在: 起点となる処理が定義されているファイルと、その処理の名前
- **実行アクター (`actor`)**: 操作主体（例: `一般ユーザー`, `バッチワーカー`）
- **参照リードモデル (`readModel` / 画面文脈)**:
  - 画面ルート（例: `/mypage`）
  - 画面コンポーネント識別子
  - 関連画面画像参照パス
  - 画面を持たないシステム（ライブラリ、コマンドラインツールなど）では、リードモデルは無い。その場合は起点の所在（公開されている処理）を入口とする。
- **完了条件 / 期待イベント (`expectedEvent`)**: 当該シナリオの完了により確定すべきドメインイベント。起点のコマンドが発生させるイベントとする（ポリシーが起点のときは、ポリシーが起動するコマンドの発生させるイベント）。1 つのシナリオの期待イベントは 1 つであり、起点がイベントを複数発生させるときは、イベントごとに別のシナリオにする。
- **達成目的 (`intent`)**: ユーザーまたはシステムが本シナリオで達成する業務上の目的（Why）。本モジュールが出すのは**意図の候補**であり、人間（PdM）が確定するまでは候補として扱う（Bounded Context の「意図」も同じ）。確定したかどうかを区別できる形（`intentStatus`: `CANDIDATE` または `CONFIRMED`）で保持する。初回の実行ではすべて `CANDIDATE` である。

## 3. 契約仕様 (Design by Contract)

### 3.1 事前条件 (Preconditions)
- 解析対象のリポジトリ構造情報、または人間によるシナリオ指定が与えられていること。

### 3.2 事後条件 (Postconditions)
- **全体マップの健全性 (Project Invariant)**:
  - 出力される `EventStormingMap` において、すべてのコマンドは1つ以上のイベントまたはポリシーに因果的に結合していること。
  - 各要素が適切な Bounded Context に割り当てられていること（分離不能時は単一コンテキストに割り当てられていること）。
  - ポリシーは、実装に存在する反応（イベントの発生を受けて別の処理を起動するコード）に対応していること。対応する実装が無いポリシーを作らないこと。
- **個別シナリオの完結性 (Task Invariant)**:
  - 出力される各 `ScenarioTarget` は、単一のコマンドまたはポリシーを起点とし、アクター、起点の所在、および完了条件（期待イベント）が過不足なく特定されていること。リードモデル（画面ルート）は、画面を持つシステムでは特定されていること。
  - 異なる起点から切り出したシナリオは、異なる起点の所在と期待イベントを持つこと。

### 3.3 不変条件 (Invariants)
- **フォールバック保証**: Bounded Context の境界が曖昧な場合、処理を中断・失敗させず、必ず「単一 Bounded Context」として一貫性を維持してモデル化すること。
- **決定論性**: 同一の入力リポジトリ情報に対して、出力される全体マップおよび個別シナリオは完全に同一であること。LLM を使う処理（ドメインイベントとコマンドの命名、意図の候補）は、出力を記録して再利用することでこれを満たす。LLM に届かないときは、命名と意図の候補を「未生成」として記録し、機械的に作った名前で埋めない。識別子は LLM の出力から作らず、コードから機械的に決まる値から作るので、未生成の項目があっても後段の処理は進む。
- **非破壊性・純粋抽出**: 解析対象のリポジトリやドキュメントを一切改変しないこと。
