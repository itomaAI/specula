# 汎用仕様抽出・検証システム 全体仕様書 (System Solution Specification)

本仕様書は、汎用仕様抽出・検証システム（Universal Spec Extraction & Verification Platform）が外部に対して提供する**ブラックボックスとしての振る舞い、大域情報モデル、および守るべき契約（事前条件・事後条件・不変条件）**を定義する。
本システムをどう実装するか（内部アルゴリズム、使用ライブラリ、具体的なパーサー等）には一切言及しない。

---

## 1. システム理念と Loom 双対モデル

### 1.1 背景と目的
ソフトウェア開発において、コードは Git で、デザインは Figma で管理されるが、「仕様」は属人化し散逸している。本システムは、既存の実装（コードおよび画面）と仕様の資料（README・ドキュメント・スキーマ定義）からドメイン仕様を客観的に奪還し、数学的に検証された仕様を「唯一の正本（Single Source of Truth）」として維持・編集・射影するプラットフォームを提供する。

### 1.2 Loom 双対構造（プロジェクト／タスク）の大域適用
本システムが取り扱う知識および処理の単位は、すべて Loom の 2 大概念に準拠してモデル化される：

1. **プロジェクト相当 (Bounded Context / System Root)**:
   - **性質**: 終わらない観点、意図（Why）、および文脈（Context）を持つ大域的な器。
   - **保持情報**:
     - `## 意図`: システムおよび各ドメイン境界の存在理由・責務。
     - `## 文脈`: ドメインイベントの連鎖（Event Storming 全体マップ）、外部との境界。
2. **タスク相当 (Individual Command)**:
   - **性質**: 単一の明確な完了条件を持つ、1本のアトミックな仕事（状態遷移・因果スライス）。
   - **保持情報**:
     - `## 依頼`: 単一の起点（Command または Policy）と実行主体（Actor）。
     - `## 前提・リードモデル`: 操作の起点となる画面・情報ビュー（Read Model）。
     - `完了条件`: 確定すべきドメインイベント（Expected Domain Event）。

概念は Bounded Context → Event Storming 全体マップ → コマンドの単位 の順に具象化される。コマンドの所属を表す項目名は `boundedContext`、完了条件を表す項目名は `expectedEvents` とする（2026-10-31 に、コマンドノード 1 つにつき単位 1 つとし、期待イベントを一覧にした）。

### 1.3 3つの基本操作（置く・畳む・移す）によるライフサイクル
- **置く（分解 / Decompose）**: システム全体から Bounded Context（プロジェクト）を同定して全体マップを作り、その全体マップからコマンドの単位（タスク）をアトミックに切り出す。全体マップを作る処理とコマンドを切り出す処理は、どちらも「置く」であり、具象化の向きに進む。
- **畳む（集約 / Fold）**: 検証・合意されたコマンドの単位の論点・不変条件を集約し、親コンテキストの文脈（仕様正本・ナレッジ）へと還元する。畳むのは検証と人間の合意の**後**であり、抽出したばかりの事実を畳むことはない。
- **移す（伝播 / Transfer）**: あるコンテキストで確定したドメインイベントを、別コンテキストのポリシー起動トリガーへと越境伝播させる。

### 1.4 事実の読み取りと評価の分離
- 本システムは、実装（コードおよび画面）に存在する振る舞いを**事実として**読み取る。読み取りの段階では「バグ」と「仕様」を区別しない。
- 全体マップとユビキタス言語辞書は、コードと資料をそのまま見せるためのものであり、言葉の意味に基づいて構造を変えない。資料とコードのずれは辞書が記録して見せるだけで、どちらが正しいかを決めない。言葉（概念モデル）とコードの構造（論理モデル）を擦り合わせて決めるのは、辞書と全体マップを受け取って利用者に提示する**別のアプリ（インタラクションビューアー）**の責務とする。このアプリは現時点では作らない。
- 反例が出ない（形式仕様としては整合している）が意図とは異なる振る舞いに注意を向ける機能は、抽出・検証の結果をレビューする**別のモジュール**の責務とする。このモジュールは現時点では作らない。
- 意思決定論点カタログの選択肢にある「バグとして修正する」は、人間が選ぶ判断であり、システムが事実を読み取る段階での区別ではない。

### 1.5 初回の実行と、2 回目以降の実行（ループ）
- 本システムは、前回の実行結果と、それに対する人間の判断を次の実行の入力とすることで、仕様の履歴を更新する。人間の判断は「前回の出力に対する反応」として、次の実行で入る。
- **初回の実行**では、人間はまだ何も判断していない。したがって、初回の意思決定論点はすべて**未決**であり、射影ビューも未決として表示する。選択肢の一つを「採択」「合意済み」として表示してはならない。
- 人間の判断を記録する欄はデータの型として用意するが、それを埋めるのは 2 回目以降の実行である。「畳む」（1.3）も 2 回目以降の実行で行う。
- 現時点で実装・検査の対象とするのは初回の実行だけである。人間の判断を受け取る画面と 2 回目以降の実行は、追加で開発する。

## 2. 外部公開インターフェース仕様 (Public Interface)

本システムは、モジュール自律性を前提とした以下の決定論的システムコマンド群を提供する。各コマンドは独立した道具として呼び出せる。下の並びは全体のパイプラインが呼ぶ順であり、モジュールの番号ではない。

### 2.1 システムコマンド一覧
1. **`DiscoverSystemContext(repo: RepositoryArtifacts) -> EventStormingMap`**
   - リポジトリ構造から Bounded Context を同定し、ドメインイベント・コマンド・ポリシー・リードモデルを束ねた全体マップを出力する（プロジェクトの構築）。全体マップは名前と意図を持たず、要素・つながり・識別子・実装の所在だけを持つ。
2. **`SliceCommands(map: EventStormingMap, selection?: CommandSelection) -> SliceResult`**（切り出したコマンド `CommandTarget[]` と、受け付けなかった利用者定義のコマンド）
   - 全体マップから、コマンドノード 1 つにつき 1 つのコマンドの単位をアトミックに切り出す（タスクの分解・配置）。ポリシーは起点にせず、起動するコマンドの単位の `invokedBy` に入れる（2026-10-31 改定）。
   - `selection` は、切り出す範囲の絞り込み条件（`filter`）と、利用者が定義したコマンド（`userDefined`）のどちらか、または両方を持つ。省略した場合は、全体マップから抽出できるコマンドをすべて切り出す。
   - 出力する各コマンドは、出どころ `origin` を持つ。全体マップから抽出したものは `EXTRACTED`、利用者が定義したものは `USER_DEFINED` とする。利用者が定義したコマンドは、全体マップに起点が存在することを確かめたうえで、抽出したコマンドと同じ形に正規化して出力する。起点が全体マップに無いコマンドは出力せず、理由を付けて呼び出し元へ返す。起点は識別子かハンドラの所在で指定し、LLM が付けた名前では照合しない。
3. **`BuildGlossary(map: EventStormingMap, repo: RepositoryArtifacts) -> Glossary`**
   - 全体マップと仕様の資料から、ユビキタス言語辞書（用語と、用語と実装名の対応）を作る。辞書にはリポジトリから機械的に拾える実装の名前をできるだけ載せるが、用語を付けて利用者に提示するのは全体マップの要素（Bounded Context・コマンド・イベント・ポリシー）だけとする。
   - 資料に記述が無い要素、どの項目にも対応しない資料の名前などのずれは、記録して見せるだけにする。
4. **`SynthesizeIntents(map: EventStormingMap, slice: SliceResult, glossary: Glossary, repo: RepositoryArtifacts) -> IntentCatalog`**
   - Bounded Context とコマンドの意図の候補を書く。意図はすべて候補であり、人間が確定するまでは候補として扱う。
5. **`ExtractContext(target: CommandTarget, sources: SourceArtifacts) -> RawContextModel`**
   - 単一のコマンドの単位を起点とし、開始境界（Inlet）から終了境界（Outlet）までの因果チェーンのみを非同期境界を跨がずにピンポイントで垂直抽出する。
6. **`TranspileFormal(facts: RawContextModel, previous?: FormalSpec) -> FormalSpec | AmbiguityReport`**
   - 事実モデルの状態変数（真偽値・列挙・整数）と、スライスごとの出口（分岐の結果）から状態と操作を組み立て、Alloy 6 の形式仕様正本へ決定論的に変換する。正本の識別子は機械的に付け（`v1`・`op1` など）、実装の変数名は正本の公開識別子に出さない。ドメインの語による表示名は LLM が付け、正本とは別の `labels` に持つ（LLM に届かなければ「未生成」）。そのため、正本のソースは LLM の結果によらない。
   - 状態を決められない式・外部への作用・食い違うスライスがあるときは、自己補完せずに曖昧性レポート（`AmbiguityReport`）を出力する。曖昧性はすべて集め、種類ごとの件数を付ける。
   - 初回は業務上の不変条件（`fact`）と守るべき性質（`assert`）を作らない（初期状態と遷移の枠組みの `fact` だけを作る）。前回の正本 `previous` との差分は初回は計算しない（`NOT_COMPUTED`）。
7. **`VerifySpecification(spec: FormalSpec, options?: SolverOptions) -> SolverReport`**
   - 形式仕様正本に対し、Alloy 6 を用いて、指定のスコープ（ステップ数の上限など）の中で検査を行い、未定義遷移・操作の重なり・到達できない操作・デッドロックの反例を報告する。初回は不変条件が無いので、不変条件の検査は「対象外」と報告する。
   - ソルバに届かないときは、報告を「未検証」とし、理由と実行しなかった検査を付ける。反例が無かった報告として扱わない。
8. **`SynthesizeLedger(report: SolverReport, spec: FormalSpec) -> DomainLedgerCatalog`**
   - 反例を、ステークホルダーが判断する論点（主張・観測事実・判断質問と、反例の種類ごとに決まった選択肢）にする。同じ状態を指す反例は 1 つの論点にまとめる。検証の状態をカタログの先頭に写す。
9. **`ProjectSpecification(spec: FormalSpec, ledger?: DomainLedgerCatalog, glossary: Glossary, req: ProjectionRequest) -> SpecificationView`**
   - 形式仕様正本および論点カタログから、仕様書（Markdown）・操作の一覧表・操作の流れ図（Mermaid）を決定論的に作る。システム全体の俯瞰図は、全体マップ（`EventStormingMap`）と辞書から作る。曖昧性レポートで止まったコマンドは、曖昧さの一覧として射影する。
   - 論点は、人間の判断の記録があるものだけを決定済みとして表示する。記録がない論点（初回の実行ではすべて）は未決として表示する。
   - `req` は表示の役割（`viewRole`: `BUSINESS`・`IMPLEMENTATION`。4.5）を持つ。`BUSINESS` では実装の名前を出さず、要素を辞書の用語で表す。`IMPLEMENTATION` では、同じ表示に実装の名前と所在を併記する。1 回の実行で両方の役割のビューを作る。実装との対応表は、役割に関係なく辞書から射影する。

## 3. 大域的契約仕様 (Global Design by Contract)

### 3.1 事前条件 (Preconditions)
1. 入力リポジトリ情報に、解析可能なコードまたはメタ情報（README、ルート定義、スキーマ等）が存在すること。
2. コマンドの単位の抽出に際しては、有効な開始エントリーポイントが特定されていること。

### 3.2 事後条件 (Postconditions)
1. **境界遵守**: 抽出される事実およびモデルは、指定されたコマンドの境界（InletからOutletまで）に閉じ、非同期境界を越えた無関係な処理を含まないこと。
2. **形式完全性**: 導出された形式仕様は検証エンジンが受け付ける形であり、**指定スコープの中で**行った検査が見つけた反例が、元の記録（検証結果レポート）に余すことなく残ること。行わなかった検査（初回の不変条件の検査、ソルバに届かなかった検査）は、行わなかったこととして記録に残ること。
   - 検証結果レポートは元の記録として、全件と、結果を再現するための実行条件（エンジンの版、SAT ソルバ、スコープ、分割の仕方）を保持する。
   - 意思決定論点カタログは元の記録の要約であり、全件を並べなくてよい。その代わり、どのレポートの反例 N 件を論点 k 件にまとめたか、従属として後ろに回した反例がどれかを必ず示す。これにより「すべての違反が、元の記録か、そこからたどれる論点のどちらかに載っている」ことを保つ。
3. **人間中心の意思決定**: 仕様の曖昧さや反例の解決をシステム自身が推測で行わず、必ず人間への意思決定論点として提示されていること。
4. **射影整合性**: 射影されたすべてのビュー（Markdown、グラフ等）が、形式仕様正本と 100% 整合していること。
5. **届かなかったことの記録**: 検証エンジンや LLM など外部の処理系に届かなかった場合、代わりの判定や定型文でその結果を埋めてはならない。届かなかったこと（どの処理系に、なぜ届かなかったか）を出力に記録し、検証結果は「未検証」、LLM が作るはずの項目は「未生成」として先へ進むこと。

### 3.3 不変条件 (Invariants)
1. **完全隠蔽性**: 最終仕様書、図式、論点カタログ、曖昧さの一覧、および形式仕様正本の**公開識別子**（概念・状態・操作・制約の名前）には、内部実装固有のフレームワーク予約語や内部変数が一切漏洩しないこと。
   - 利用者向けの表示（役割 `BUSINESS`）には、ファイルのパス・関数名・行番号・コードの断片を出さない。実装との対応は、ユビキタス言語辞書と、そこから作る実装との対応表に持つ。役割 `IMPLEMENTATION` の表示は、この対応を引いて実装の名前と所在を併記してよい。
   - 原本との対応を逆引きするための出どころ注釈（例: `@source`）は、形式仕様正本の中に保持してよい。これは公開識別子ではなく、射影ビューと論点カタログを作るときに必ず取り除く（役割 `IMPLEMENTATION` の付録に正本のソースを載せるときを除く）。
2. **決定論性（担当ごとに約束を分ける）**:
   - **決定論的な処理**（CommandExtractor の全体マップの作成とコマンドの切り出し、ContextExtractor の事実抽出、FormalSolver の検証、SpecProjector の射影、および GlossaryBuilder・IntentSynthesizer・FormalTranspiler のうち機械的な処理）: 同一の入力から、いつ何度実行しても完全一致（差分ゼロ）の出力を返すこと。FormalSolver は「同一の実行条件（エンジンの版、SAT ソルバ、スコープ、分割の仕方）のもとで」一致する。
   - **LLM を使う処理**（GlossaryBuilder の用語、IntentSynthesizer の意図の候補、FormalTranspiler のドメイン語彙への言い換え、LedgerSynthesizer の自然言語化）: 一度出した結果を記録し、再実行ではその記録を使うことで一致させること。記録を作り直すのは、入力が変わったとき、または人間が指示したときに限る。
   - どの処理が LLM を使うかは、全体基本設計書（`system_solution.design.md`）の「LLM の担当範囲」に一覧する。
3. **フォールバック保証**: Bounded Context の境界が曖昧な場合でも処理を停止させず、単一コンテキストとして一貫性を維持してモデル化すること。
4. **非破壊性**: 入力されたソースコード、画面画像、ドキュメント原本を一切改変しないこと。

## 4. 言葉と識別子の決まり（2026-10-31 決定。Issue #40）

この章は、Issue #40 の議論で決まった言葉と識別子の決まりを定める。ほかの章と各モジュールの文書の本文、および内部の呼び名は、2026-10-31 にこの章に合わせて書き換えた。本文では、4.2 の「コマンド」の単位を「コマンド」と書き、全体マップのコマンドのノードと区別したいところでは「コマンドの単位」と書く。

### 4.1 イベントストーミングの全体マップが表すもの
- 全体マップは**業務の流れ**を表す。処理の流れ（呼び出しの順序）を表すものではない。そのため、利用者向けの地図には、モジュールや関数の名前を出さない。実装の名前と所在は、識別子とともに出力に持ち、役割 `IMPLEMENTATION` の表示でだけ併記する（3.3）。
- 付箋どうしの矢印のうち、全体マップに載せるのは、実装から確定できるものだけである。
- 実装からは確定できない矢印（例: 出力を見た利用者の操作によって、もう一度パイプラインが回る矢印）は、根拠とともに推測として持ち、人間が根拠を承認したら確定し、否決したら消す。否決されたという記録は残す。実装と仕様が一致しないときに、同じ矢印が再び提案されうるためである。この「推察した矢印」は既存の機能の改修ではなく追加の機能であり、現時点では作らない。

### 4.2 言葉
| 言葉 | 指すもの | 表示の id |
| :-- | :-- | :-- |
| コマンド | 全体マップのコマンドノード 1 つを起点に、そのコマンドが発生させるイベントのすべてまでを垂直に追った単位。これまで「シナリオ」と呼んでいたもの（2026-10-31 改定。改定前は、起点が発生させるイベント 1 つまでを単位とし、ポリシーも起点にしていた） | `C-01` の形 |
| シナリオ | 特定のアクションから、別のイベントなどに至るまでの、複数の付箋をまたぐ経路。起点の種類によらず、付箋をまたぐものはシナリオとする | 次の段で決める |
| ポリシー | 「イベント X が起きたら、コマンド Y を起動する」反応のルール | （変更なし） |

- これまでポリシーを起点としていた単位は、**ポリシーから呼ばれるコマンド**として扱う。コマンドの詳細では、呼び出し元のポリシーを補助情報として表示する。全体マップでは、ポリシーを矢印として持ち続ける。
- 利用者が定義した単位の受け入れ（2.1 の `SliceScenarios` の `userDefined`）は、起点を 1 つだけ受け取り、抽出した単位と同じ形に正規化する。そのため、これは**利用者が定義したコマンド**として扱う。4.2 の新しい意味のシナリオを利用者が定義して受け入れる仕組みは、シナリオを切り出す機能とともに作るものであり、現時点では作らない。

### 4.3 内部の呼び名の置き換え（2026-10-31 確定）
内部の呼び名も 4.2 に合わせて、次のとおり置き換える。置き換えは次の段の PR で行う。

| いまの呼び名 | 新しい呼び名 | 備考 |
| :-- | :-- | :-- |
| `ScenarioExtractor` | `CommandExtractor` | 全体マップの作成も行うモジュールだが、この名前とする |
| `ScenarioTarget` | `CommandTarget` | |

| 出力の `scenarios/` | `commands/` | 実行の報告（`run_report.json`）の項目も同じ規則で置き換える |

### 4.4 列挙に類する文字列
- 列挙型の値と、それに類する使い方をする文字列（種類・状態・役割など、決まった値の中から 1 つを選ぶもの）は、アッパースネークケース（例: `NOT_GENERATED`）に統一する。例外は作らない。
- LLM のタスク名は、列挙の値ではなく、LLM への依頼の種類を識別する名前として扱う。タスク名の命名規則は「`<処理の名前>.<内容>` を、小文字の英字・数字とハイフンで書く」とする（例: `glossary.term-context`、`intent.context`、`m2.ambiguity-question`、`m4.issue-text`）。
- 置き換える値の一覧は、次の段の PR で各モジュールの文書とともに示す。

### 4.5 表示の役割
| 識別子 | 画面の表示名 | これまでの識別子 |
| :-- | :-- | :-- |
| `BUSINESS` | 業務 | `PdM` |
| `IMPLEMENTATION` | 実装 | `Eng` |

- URL では識別子を小文字にして渡し（例: `business`）、読むときに大文字へ戻す。
- 列挙に無い値は、既定の値に読み替えずにエラーにする。
