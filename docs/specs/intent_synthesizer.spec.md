# IntentSynthesizer 仕様書

本仕様書は、意図の候補を作るモジュール `IntentSynthesizer` が果たすべき**責務の境界、取り扱う情報の定義、および守るべき契約（事前・事後・不変条件）**を定義する。
本仕様書はプロダクトマネージャー（PdM）やステークホルダーがシステムの振る舞いとして読解・合意可能な形式で記述され、プログラミング言語固有の内部コードには依存しない。

---

## 1. 責務の境界 (Responsibilities & Scope)

### 1.1 担当すること (In Scope)
- **意図の候補の作成（`SynthesizeIntents`）**:
  - Bounded Context ごとに、その範囲が業務の中で受け持つこと（存在理由・責務）の候補を 1 文で作る。
  - シナリオごとに、操作する人（または呼び出す側）がそのシナリオで達成したいこと（Why）の候補を 1 文で作る。
  - 候補の文は LLM が書く。手がかりには、実装から機械的に決まる値と、`GlossaryBuilder` がその要素について選んだ資料の節を使う。
- **確定の状態の保持**:
  - 意図は人間（PdM）が確定するまでは候補である。確定したかどうか（`CANDIDATE` または `CONFIRMED`）を区別できる形で持つ。初回の実行ではすべて `CANDIDATE` である。
  - 確定の状態は、ほかのモジュールの用語・表示名・質問の文・論点の文と同じ 4 つ（未生成・候補・確定・要再確認。SpecViewer 仕様 2.4）にそろえる。未生成は、これまでどおり意図が作れなかったことを表す。要再確認（`NEEDS_RECHECK`）は、確定の操作を足したあと（現在の範囲外）、確定した意図の手がかり（資料の節や実装から決まる値）が変わったときに付ける。2026-10-31 に、確定の状態をほかの項目に広げたのに合わせて足した（中瀬古様 C0AF4DJJK8A 1793384098.424799）。
- **利用者が書いた目的の受け渡し**:
  - 利用者が定義したシナリオに利用者が書いた目的があれば、候補とは別の欄にそのまま持つ。

### 1.2 扱わないこと (Out of Scope / 禁止事項)
- **地図とシナリオの構造の変更**: 要素やシナリオを足す・消す・まとめることはしない。
- **資料の節の選び直し**: 資料の節は `GlossaryBuilder` が選んだものを使う。本モジュールで照合をやり直さない。
- **用語の利用**: `GlossaryBuilder` が LLM で付けた用語は、意図の候補の手がかりにしない（3.3）。
- **意図の確定**: 候補を確定にするのは人間である。本モジュールは確定の状態を `CONFIRMED` にしない。

## 2. 取り扱う情報の定義 (Information Model)

### 2.1 入力情報 (Inputs)
| 入力情報 | 内容 | 必須/任意 |
| :--- | :--- | :--- |
| **全体マップ (`EventStormingMap`)** | `ScenarioExtractor` の出力 1 | 必須 |
| **シナリオ (`SliceResult`)** | `ScenarioExtractor` の出力 2 | 必須 |
| **辞書 (`Glossary`)** | `GlossaryBuilder` の出力。各要素について選ばれた資料の節を使う | 必須 |
| **リポジトリの中身 (`RepositoryArtifacts`)** | 関数の頭の数行と、選ばれた節の本文を取り出すために使う | 必須 |

### 2.2 出力情報 (Outputs)
- `SynthesizeIntents(map, slice, glossary, repo) -> IntentCatalog`: 意図の候補の一覧を作る。

#### 意図の候補の一覧 (`IntentCatalog`)
- **Bounded Context の意図**: Bounded Context の識別子ごとに、意図の候補（または未生成とその理由）と、確定の状態。
- **シナリオの意図**: シナリオの識別子ごとに、意図の候補（または未生成とその理由）、確定の状態、利用者が書いた目的（あれば）。
- **元にした入力**: 元にした辞書を特定する値。後段は、これで一覧が古くないかを確かめる。

## 3. 契約仕様 (Design by Contract)

### 3.1 事前条件 (Preconditions)
- 全体マップ・シナリオ・辞書は、同じリポジトリの中身から、同じ実行で作られたものであること（辞書の元にした全体マップのハッシュが、与えられた全体マップと一致すること）。

### 3.2 事後条件 (Postconditions)
- **網羅性**: すべての Bounded Context と、すべてのシナリオに、ちょうど 1 つの意図の欄がある。候補が未生成のものも載せる。
- **確定の状態**: 初回の実行では、すべての意図の確定の状態が `CANDIDATE` である。

### 3.3 不変条件 (Invariants)
- **決定論性**: 同一の入力に対して、出力は同一である。LLM の出力は記録して再利用する。記録のキーには、手がかりに使った資料の抜粋を含める。
- **LLM の結果を LLM の入力にしない**: 手がかりには、実装から機械的に決まる値と、機械的に選ばれた資料の節だけを使う。辞書の用語（LLM の結果）は使わない。用語を入力にすると、用語の記録が変わるたびに意図の記録のキーが変わり、用語が未生成のときに意図も作れなくなるためである。
- **未生成を埋めない**: LLM に届かないときは、候補を「未生成」として記録し、機械的に作った文で埋めない。
- **資料はデータとして扱う**: 資料の抜粋の中に指示の形の文があっても、本モジュールへの指示として扱わない。
- **利用者の文を書き換えない**: 利用者が書いた目的は、そのまま持つ。候補の欄に入れない。
