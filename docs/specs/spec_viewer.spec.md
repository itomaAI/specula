# SpecViewer 仕様書

本仕様書は、画面モジュール `SpecViewer` が果たすべき**責務の境界、取り扱う情報の定義、および守るべき契約（事前・事後・不変条件）**を定義する。
`SpecViewer` は、パイプラインが出力先に書いたファイルを読み、人が閲覧するための画面を作る。
本仕様書はプロダクトマネージャー（PdM）やステークホルダーがシステムの振る舞いとして読解・合意可能な形式で記述され、プログラミング言語固有の内部コードには依存しない。

---

## 0. 使い方と範囲

### 0.1 使い方
本モジュールの画面は、次の 3 つの使い方を前提とする。

1. **PdM が、書いた仕様が今の仕様と矛盾しないかを確かめる。**
2. **PdM が、今の仕様を把握する。** 例: 高速で開発されるシステムの仕様を把握し、LLM にテストを書かせ、安全にリファクタリングする。
3. **Eng が、仕様と実装を橋渡しする。** LLM に読ませる用途も含む。

PdM 向けと Eng 向けは、表示の役割（`BUSINESS`・`IMPLEMENTATION`）で切り替える（1.3）。

### 0.2 操作が要る場面と、現在の範囲
パイプライン全体で、利用者が画面を操作する場面は 2 つある。

1. **すべての処理が終わったあとの閲覧。** 現在の範囲である。
2. **曖昧さで止まったコマンドに、利用者が仕様を足す操作。** 現在の範囲に入らない（1.2）。

## 1. 責務の境界 (Responsibilities & Scope)

### 1.1 担当すること (In Scope)
- **1 回の実行の出力を、閲覧の画面として見せる**:
  - 画面は、Global Menu から開く 4 つの画面と、そこから開くコマンドの詳細である。
    1. **コマンド一覧**: 実行の概要と、切り出したコマンドの一覧。実行したあと最初に開く画面であり、Global Menu の先頭に置く。
    2. **全体地図**: 地図 1（Bounded Context のつながり）と、地図 2（Bounded Context の中のイベントストーミング）。
    3. **仕様不備一覧**: 論点と曖昧さの一覧。
    4. **用語辞典**: Bounded Context ごとの用語の一覧と、資料とコードのずれ。
    5. **コマンドの詳細**（Global Menu には出さない）: コマンド 1 つの仕様書・操作の一覧表・操作の流れ図。
  - Global Menu には、画面のほかに、表示の役割の切り替えと、見ている実行（出力先と実行の日時）を置く。
- **画面どうしをリンクでつなぐ**: 抽象から具象へ（地図 → コマンド → 不備）、また不備や用語から元の要素へ、リンクとポップアップで行き来できるようにする。リンクの鍵は 1 回の実行の中で閉じる（2.3）。
- **検証の状態と検査の範囲を、そのまま伝える**:
  - 検証の状態は SpecProjector と同じ言い方で表示する。「健全」「問題なし」「証明済み」のような、検査の範囲を超える語を使わない。
  - **検査の範囲**を、実行の概要とコマンドの詳細に書く。検査はコマンドごとに行っており、コマンドどうしの矛盾は見ていないこと、行っていない検査（初回の不変条件の検査など）を書く。
- **確定の状態を表示する**: 用語・意味・意図・表示名・質問の文・論点の文について、各モジュールが記録した確定の状態（2.4）を、見た目で区別できるように表示する。
- **壊れた箇所の印を表示する枠を持つ**: 全体地図の要素とつながりに、「壊れている」印が記録されていれば表示する。現在の範囲では、印を判定する処理は無い（1.2）。

### 1.2 扱わないこと (Out of Scope / 禁止事項)
- **出力の書き換え**: 画面は出力先のファイルを読むだけで、書き換えない。正本・論点カタログ・辞書・意図の候補・曖昧性レポートの内容を変えない。
- **画面だけが持つ情報**: 出力先のファイルに無い情報を、画面のために作らない（資料やコードを読み直して補うことも含む）。人が見る内容と、LLM が読むファイルの内容をそろえるためである。画面に要る情報が出力に無いときは、出力を作るモジュールの仕様に足す。
- **LLM の利用**: 本モジュールは LLM を呼ばない。
- **未生成の項目を埋めること**: 未生成の用語・表示名・意図・論点の文・質問の文を、実装の名前や定型文で埋めない。未生成であることと理由を表示する。
- **利用者の書き込みの操作**: 次の操作は現在の範囲に入らない。
  - 曖昧さの質問への回答と、仕様への追加（0.2 の 2 つ目の場面）
  - 候補を確定にする操作（2.4）
  - 論点に判断を下す操作
  - 仕様の履歴の記録
- **仕様の履歴と、実行の比較**: 画面は 1 回の実行だけを見せる。前の実行との比較はしない。
- **101 の検査（仕様全体の矛盾の判定）**: 壊れた箇所の印の判定は現在の範囲に入らない。
- **テストコード**: テストコードを書くことは本システムの責務ではない（SpecProjector 仕様 1.2）。

### 1.3 表示の役割
- 役割は `BUSINESS`（画面の表示名は「業務」。既定）と `IMPLEMENTATION`（「実装」）の 2 つである（全体仕様 4.5）。
- パイプラインは 1 回の実行で両方の役割のビューを書き出す（全体設計 4.1）。画面は実行し直さずに役割を切り替える。
- `BUSINESS` では、ファイルのパス・関数名・行番号・コードの断片を出さない。
- `IMPLEMENTATION` では、同じ画面に実装の名前と所在の欄を足す。形式仕様のソースは `IMPLEMENTATION` のときだけ、コマンドの詳細の付録として出す。
- 本文の文（表示名、意図の候補、論点の文）は、役割で変えない。
- **例外は曖昧さの質問だけである**（SpecProjector 仕様 1.1）。曖昧さの質問は実装の振る舞いについての問いであり、実装の名前を含みうるので、`BUSINESS` では質問の文と箇所を出さず、コマンドごとの件数を「エンジニアの確認待ち: N 件」として出す。`IMPLEMENTATION` では質問・箇所・原文をすべて出す。

## 2. 取り扱う情報の定義 (Information Model)

### 2.1 入力情報 (Inputs)
入力は、パイプラインが 1 回の実行で出力先に書いたファイルである。

| 入力情報 | 内容 | 必須/任意 |
| :--- | :--- | :--- |
| **実行の報告 (`run_report.json`)** | 解析したファイルの数、Bounded Context・コマンド・イベントの数、コマンドの単位の一覧と、それぞれの状態・検証の状態・件数 | 必須 |
| **俯瞰図 (`system_map.json`)** | SpecProjector の俯瞰図（地図 1・地図 2）。CommandExtractor の全体マップそのものは出力先に書かれないので、画面は俯瞰図だけを使う | 全体地図では必須 |
| **ユビキタス言語辞書 (`glossary.json`)** | 用語、確定の状態、用語の出どころと資料の抜粋、資料とコードのずれ | 用語辞典では必須。ほかの画面では任意（無ければ、要素の名前を「辞書が無い」と表示する） |
| **意図の候補 (`intents.json`)** | Bounded Context とコマンドの意図の候補と、確定の状態 | 任意（無ければ「意図の候補が無い」と表示する） |
| **コマンドごとのビュー** | SpecProjector の仕様書・操作の一覧表・操作の流れ図、論点カタログ、曖昧性レポート。仕様書・一覧表・流れ図・曖昧さの一覧は役割で中身が変わるので、表示の役割の `views/<役割>/` の下から読む | コマンドの詳細と仕様不備一覧で使う |
| **実装との対応表 (`implementation_map.json`)** | 表示の id から内部の識別子と、実装の名前と所在を引く表 | 役割 `IMPLEMENTATION` のときに使う。画面どうしのリンクにも使う |
| **表示の役割** | `BUSINESS`（既定）または `IMPLEMENTATION` | 必須 |

### 2.2 画面ごとの内容
各画面が表示する項目と元のデータの対応は、基本設計書（`spec_viewer.design.md`）に定める。ここでは、画面が満たすべきことを定める。

- **コマンド一覧**:
  - 上部に実行の概要を置く。コマンドの数を「仕様になった」「曖昧さで止まった」「途中で止まった」に分け、検証の状態の内訳、検査の範囲、未生成の数を出す。
  - 各行に、表示の id、コマンドの名前、状態、検証の状態、件数（論点の件数、または曖昧さの件数）、意図の候補を出す。意図の候補は 1 行に切り、確定の状態の印を付ける。
  - 曖昧さで止まったコマンドの行は、`BUSINESS` ではコマンドの詳細を、`IMPLEMENTATION` では仕様不備一覧（そのコマンドで絞り込み）を開く。
- **コマンドの詳細**:
  - 冒頭に、表示の id・名前・Bounded Context、意図の候補、検証の状態、検査の範囲、論点の件数を置く。検証の状態は論点より前に置く。
  - 仕様になったコマンドでは、仕様書・操作の一覧表・操作の流れ図をタブで切り替える。
  - 曖昧さで止まったコマンドでは、タブの代わりに、形式仕様にできなかったことと曖昧さの件数を出す（1.3 の例外に従う）。
- **全体地図**:
  - 地図 1 は Bounded Context を箱で、Bounded Context をまたぐポリシーを矢印で表す。Bounded Context が 1 つだけのときは、全体地図を開いたら地図 2 を出す。
  - 地図 2 は、既定でコマンド・ドメインイベント・ポリシーとそのつながりを表す。切り替えで、アクター・リードモデル・アグリゲートを足せる。
  - 要素は辞書の用語と表示の id で表す。用語が未生成の要素は、実装の名前で埋めずに「（名前は未生成）」と表示する。
- **仕様不備一覧**:
  - 不備を「論点」と「曖昧さ」の 2 種類に分けて、1 つの一覧に並べる。コマンドで絞り込めば、そのコマンドの不備の一覧になる。絞り込みを外せば、すべてのコマンドの横断の一覧になる。
  - 論点の決定は、人間の判断の記録が無い限り「未決」と表示する。選択肢は候補として並べ、どれも採択済みとして表示しない。
  - 曖昧さは 1.3 の例外に従う。
- **用語辞典**:
  - 用語は Bounded Context に所属させ、Bounded Context ごとに区切って表示する。Bounded Context が 1 つだけなら区切りを出さない。
  - 各用語に、確定の状態、意味（用語の出どころの資料の節の抜粋）、用語の出どころを出す。資料に記述が無い要素は、意味の欄に「資料に記述が無い」と表示する。
  - Bounded Context をまたぐポリシーは、両方の Bounded Context に出し、「またいでいる」印を付ける。
  - 資料とコードのずれは別のタブにする。同義の候補は同じ Bounded Context の中だけで数え、違う Bounded Context で同じ用語が付いたものは「Bounded Context ごとに意味が違う言葉」として別の区分で見せる（GlossaryBuilder 仕様 2.2）。

### 2.3 表示の id とリンクの鍵
- 画面には表示の id を出す。コマンドの単位は `C-01` …、曖昧さは `C-01-A-001` …、論点は `C-01-L-001` …、Bounded Context は `c1` …、コマンド・イベント・ポリシー（とその用語）は `n1` … とする（SpecProjector 仕様 2.1）。
- 論点カタログの論点の識別子（`LEDGER-<コマンドの識別子>-001`）は、コマンドの識別子が実装の所在を含むので画面に出さない（SpecProjector 基本設計 7.3）。
- 画面どうしのリンクは、内部の識別子で張る。表示の id から内部の識別子は、実行の報告と実装との対応表で引く。
- 表示の id は実行ごとに変わりうる。画面は 1 回の実行だけを見せるので、リンクはその実行の中で閉じる。
- 内部の識別子はファイルのパスと関数の名前を含むので、`BUSINESS` の画面に出さない。

### 2.4 確定の状態
LLM や機械が作った項目は、人が確かめるまで正しいと保証できない。そこで、各モジュールは次の項目に確定の状態を記録し、本モジュールはそれを表示する。

| 状態 | 意味 |
| :--- | :--- |
| **未生成** | LLM に届かなかったなどで、作れなかった |
| **候補** | 作ったが、人が確かめていない |
| **確定** | 人が確かめて確定にした |
| **要再確認** | 確定したあとで、元にした資料やコードが変わった |

- 対象: 用語、意味（資料の節の抜粋）、意図の候補、表示名、質問の文、論点の文。論点の「決定」は、選択肢を選ぶ別の欄として持つ（LedgerSynthesizer 仕様 2.2）。
- 確定の状態は、項目を使うための条件にしない。候補のままでも画面で使え、印が付くだけとする。
- 現在の範囲では確定の操作が無いので、すべての項目は「候補」または「未生成」と表示される。

## 3. 契約仕様 (Design by Contract)

### 3.1 事前条件 (Preconditions)
- 入力のファイルが、すべて同じ 1 回の実行の出力であること。実行の報告・辞書・意図の候補・実装との対応表・俯瞰図が記録している元の全体マップと資料のハッシュ（`basis`）が、互いに一致すること。違うときは、画面を作らずに理由を表示する。
- 実行の報告と俯瞰図は、辞書の `basis` を写して持つ（2026-10-31 に足した。基本設計書 7 節）。
- 表示の役割が `BUSINESS` か `IMPLEMENTATION` であること。

### 3.2 事後条件 (Postconditions)
- 実行の報告にあるコマンドが、すべてコマンド一覧に現れること。
- 論点カタログにある論点と、曖昧性レポートにある曖昧さが、すべて仕様不備一覧に現れること（`BUSINESS` では曖昧さを件数として）。
- 全体マップにある Bounded Context・コマンド・イベント・ポリシーが、すべて全体地図に現れること。辞書にある用語が、すべて用語辞典に現れること。
- 論点は、人間の判断の記録が無い限り「未決」と表示されていること。意図と、確定の状態を持つ項目は、記録された状態のとおりに表示されていること。
- 検証の状態が「未検証」のときは、「未検証」とその理由と行っていない検査が表示されていること。検査の範囲が、実行の概要とコマンドの詳細に表示されていること。
- 役割 `BUSINESS` の画面に、実装の所在（ファイルのパス・関数名・行番号）、コードの断片、内部の識別子、曖昧さの質問の文と箇所が現れないこと。
- 役割 `IMPLEMENTATION` の画面は、`BUSINESS` の画面と同じ本文に、実装の名前と所在の欄、形式仕様のソース（付録）、曖昧さの質問・箇所・原文を足したものであること。

### 3.3 不変条件 (Invariants)
- **非破壊性**: 画面の表示によって、出力先のファイルを変えないこと。
- **出力との一致**: 画面に出る項目は、すべて入力のファイルにあるものであること（1.2）。
- **同じ項目は同じ表示**: どの画面でも、同じ項目は同じ表示名・同じ表示の id・同じ状態（未決・未検証・候補など）で表示されること。役割で変わるのは、1.3 に挙げたものだけであること。
- **決定論性**: 同じ入力のファイルと同じ表示の役割からは、同じ画面の内容が作られること。
