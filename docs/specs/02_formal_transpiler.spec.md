# FormalTranspiler 仕様書

本仕様書は、形式仕様変換モジュール `FormalTranspiler` が果たすべき**責務の境界、取り扱う情報の定義、および守るべき契約（事前・事後・不変条件）**を定義する。
本仕様書はプロダクトマネージャー（PdM）やステークホルダーがシステムの振る舞いとして読解・合意可能な形式で記述され、特定の形式言語（Alloy等）の実装構文には依存しない。

---

## 1. 責務の境界 (Responsibilities & Scope)

### 1.1 担当すること (In Scope)
- **多層システム事実モデルから形式仕様コードへの決定論的変換**:
  - 多層システム事実モデル（UI、API、バッチ、DBスキーマ）を入力とし、形式仕様コードを合成・出力する。
  - **実装詳細の完全隠蔽**: 内部変数名、ライブラリ名、フレームワーク予約語を排除し、業務ドメインの語彙（概念、状態、操作、制約）へ昇華・抽象化する。
  - **前版仕様との意味論的差分特定**: 前回の形式仕様正本が存在する場合、どの概念・操作・制約が追加・変更・削除されたかを特定する。
- **仕様の曖昧性検知と人間への補完要求 (Ambiguity Detection & Human Clarification)**:
  - 事実モデルの中に「暗黙の仮定」「条件分岐の欠落」「状態の曖昧さ」が存在し、一意な形式仕様へ落とせない場合、**無理な推測による穴埋めを拒否し、曖昧性レポート（`AmbiguityReport`）を出力して人間（PdM）へ補完を促す**。

### 1.2 扱わないこと (Out of Scope / 禁止事項)
- **数学的検証の実行**: 全状態空間探索やモデル検査、反例の探索は行わない（形式仕様の構築に閉じる）。
- **人間向けドキュメント（Markdownや図式）の射影**: 自然言語文書やグラフなどの可視化ビューの生成は行わない。
- **推測による曖昧性の勝手な解決**: 曖昧な事実をプログラミング的推測で自己修復・捏造することは固く禁ずる。

## 2. 取り扱う情報の定義 (Information Model)

### 2.1 入力情報 (Inputs)
| 入力情報 | 内容 | 必須/任意 |
| :--- | :--- | :--- |
| **システム客観事実モデル (`RawContextModel`)** | UI・API・バッチ・DBスキーマの構造化事実データ | 必須 |
| **前版 形式仕様正本 (`PreviousFormalSpec`)** | 過去のイテレーションで合意・コミットされた形式仕様コード | 任意（初回は null） |

### 2.2 出力情報 (Outputs)
以下のいずれかを出力する：

1. **`形式仕様コード (FormalSpecification)`** 【変換成功時】:
   - **ドメイン概念・構造**: システムに存在する主体、データエンティティ、画面ブロック
   - **状態空間**: ライフサイクルを通じて変化する離散状態集合
   - **操作（コマンド）**: ユーザー操作やAPI呼び出しに伴う状態遷移と事前・事後条件
   - **業務ルール・大域制約**: システム全体で常に維持されるべき不変条件
   - **受入検証プロパティ**: ソルバによって証明されるべき安全要求
   - **意味論的差分サマリ**: 前版正本との比較による追加・変更・削除の要約
2. **`仕様曖昧性レポート (AmbiguityReport)`** 【曖昧性検知時】:
   - 形式化を阻害している曖昧な箇所（どの操作・どの分岐・どのデータか）の指摘
   - 人間（PdM）が補完・明確化すべきドメイン判断質問のリスト

---

## 3. 契約仕様 (Design by Contract)

### 3.1 事前条件 (Preconditions)
- 入力される `RawContextModel` が空でなく、有効な構造化事実を含んでいること。

### 3.2 事後条件 (Postconditions)
- **分岐 A (成功時)**: 入力事実に曖昧さがない場合、ソルバでコンパイル可能な完全な形式仕様コードが出力されること。
- **分岐 B (曖昧性検知時)**: 実装コードや画像から一意な仕様が導けない場合、必ず `AmbiguityReport` が出力され、人間へ意思決定が委ねられること。

### 3.3 不変条件 (Invariants)
- **完全隠蔽性**: 内部の変数名や実装固有のキーワードが、形式仕様の公開識別子として漏洩しないこと。
- **トレーサビリティの保持**: ドメイン語彙へ昇華された各要素には、原本コードとの対応関係を逆引き検証できるよう、アノテーションとして出どころの証跡を保持すること。
- **決定論性**: 同一の入力に対して、いつ何度実行しても、出力結果（仕様コードまたは曖昧性レポート）は完全に同一であること。
