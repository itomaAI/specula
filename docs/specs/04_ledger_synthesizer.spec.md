# LedgerSynthesizer 仕様書

本仕様書は、論点合成モジュール `LedgerSynthesizer` が果たすべき**責務の境界、取り扱う情報の定義、および守るべき契約（事前・事後・不変条件）**を定義する。
本仕様書はプロダクトマネージャー（PdM）やステークホルダーがシステムの振る舞いとして読解・合意可能な形式で記述され、プログラミング言語固有の内部コードには依存しない。

---

## 1. 責務の境界 (Responsibilities & Scope)

### 1.1 担当すること (In Scope)
- **検証結果（反例または証明成功）から人間向け意思決定論点への逆翻訳**:
  - 検証結果レポート（機械的な反例・未定義遷移データ）を入力とし、非専門家（ステークホルダー・意思決定者）が判断可能な論点カタログ（`DomainLedgerCatalog`）へ変換する。
  - 各反例を「本来あるべき主張（Claim）」「観測された事実（Observation）」「判断質問（Domain Question: Is this intended?）」および「採りうる3つの選択肢」として構造化する。
  - **論点の因果依存分析と根本論点の優先提示 (Root-Cause Prioritization & Grouping)**:
    - 反例同士に因果的な依存関係が存在する場合（根本的な仕様の曖昧さが解消されることで従属反例群が解消する構造）、**因果関係の起点にある「先行依存のない根本論点」のみを特定して最優先で人間に提示**する。
    - 互いに依存のない独立した論点群は、コンポーネントやシナリオ単位で**グルーピング**して提示し、人間が1つの判断に集中して個別の意思決定を進められるようにする。
  - **証明成功時の確定推奨（Proof Success Lock）**: 矛盾や反例がゼロ件（健全）であった場合、「モデル検査により指定スコープ内で不変条件が破られないことが証明された」という事実を、仕様ロック（API契約固定）の推奨合意エントリとして合成する。

### 1.2 扱わないこと (Out of Scope / 禁止事項)
- **仕様の採否の自己決定**: 人間に代わって仕様を勝手に確定しない（意思決定は人間に委ねる）。
- **機械語の露出**: ASTノードIDや数式記号を剥き出しで人間向け質問文に含めない。
- **ソルバ自体の再実行**: 状態空間の探索やモデル検査自体の実行は行わない（与えられた検証レポートの解釈・合成に閉じる）。

## 2. 取り扱う情報の定義 (Information Model)

### 2.1 入力情報 (Inputs)
| 入力情報 | 内容 | 必須/任意 |
| :--- | :--- | :--- |
| **検証結果レポート (`SolverReport`)** | 状態空間探索によって検出された未定義遷移および最小反例トレース | 必須 |
| **形式仕様正本 (`FormalSpec`)** | アノテーション（UI文言やシナリオ名）を復元するための形式仕様コード | 必須 |

### 2.2 出力情報 (Outputs)
- **`意思決定論点カタログ (DomainLedgerCatalog)`**:
  - **論点ID**: 一意な識別子（例: `LEDGER-001`）
  - **対象シナリオ**: どの業務シナリオに関する論点か
  - **主張 (Claim)**: 本来あるべきドメインの前提
  - **観測事実 (Observation)**: ソルバが検出した欠落・反例の平易な説明
  - **判断質問 (Domain Question)**: 「〜の状態のとき、〜を非活性とすべきですか？それともエラーとすべきですか？」という問い
  - **選択肢 (Options)**: [仕様化する, バグとして修正する, 既知の例外として許容する]
    - 「仕様化する」を選ぶときは、仕様の中身（例: 非活性にするか、エラーにするか）も選ぶ。判断質問はこの中身を問う形で書いてよい。
  - **従属する反例**: この論点が解消されると解消する、後ろに回した反例の一覧（元の記録の中の識別子で示す）
- **要約の範囲（カタログ全体に 1 つ）**:
  - 要約の元にした `SolverReport` の識別子と、その実行条件
  - 元の記録の反例の件数 N と、まとめた論点の件数 k
  - 形式仕様正本の版。正本がこれより新しくなった場合、カタログが古くなったことを示す印

## 3. 契約仕様 (Design by Contract)

### 3.1 事前条件 (Preconditions)
- `SolverReport` と `AlloySpec` の対象シナリオが一致していること。

### 3.2 事後条件 (Postconditions)
- レポートに含まれるすべての未定義遷移・違反トレースが、いずれかの論点エントリから**たどれる**こと。根本論点として提示されるか、根本論点に従属する反例として紐付けられるかのどちらかである。
- 各論点に、専門知識不要な自然言語による判断質問と3つの明確な選択肢が含まれていること。
- カタログに**要約の範囲**が記録されていること（2.2 を参照）。

### 3.3 不変条件 (Invariants)
- **推測排除の中立性**: システム自身が勝手な推測で仕様の穴を埋めず、必ず「未決定論点」として中立に人間に問うこと。

### 3.4 元の記録と要約の関係
- `SolverReport` は元の記録、`DomainLedgerCatalog` はその要約（コピー）である。「漏れなく」の約束は元の記録に課され、本モジュールは「どこまでを、どうまとめたか」を示すことで整合を保つ（Loom で文脈を畳むときに「… まで／N 件」を書くのと同じ流儀）。
- 本モジュールは元の記録を書き換えない。
- 形式仕様正本が更新されたら、古い `SolverReport` から作ったカタログは古いと示し、再検証を促す。人間がすでに合意した論点の結果は、その印によって消えたり上書きされたりしない（全体アーキテクチャ 4.3 の「決定事項の不破壊性」）。
