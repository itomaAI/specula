# SpecProjector 仕様書

本仕様書は、仕様射影モジュール `SpecProjector` が果たすべき**責務の境界、取り扱う情報の定義、および守るべき契約（事前・事後・不変条件）**を定義する。
本仕様書はプロダクトマネージャー（PdM）やステークホルダーがシステムの振る舞いとして読解・合意可能な形式で記述され、プログラミング言語固有の内部コードには依存しない。

---

## 1. 責務の境界 (Responsibilities & Scope)

### 1.1 担当すること (In Scope)
- **形式仕様正本と論点カタログから、人が読むビューを決定論的に作る**:
  - 正本である形式仕様（`FormalSpec`）と、論点カタログ（`DomainLedgerCatalog`）を入力とし、利用者が指定した表現形式のビュー（Specification View）を作る。
  - 表現形式は次の 3 つである。
    1. **仕様書**: Markdown の文書。シナリオの意図の候補、状態、環境が決める条件、操作ごとの条件と書き込みと結果、検証の状態、論点を、表示名を使って書く。
    2. **操作の一覧表**: 操作ごとに、実行できる条件・結果・状態の変化・関わる論点を並べた表。
    3. **操作の流れ図**: シナリオの起点から、操作ごとの条件と書き込みを経て結果に至る図（Mermaid）。
- **システム全体の俯瞰図を 2 階層で作る**: 全体マップ（`EventStormingMap`）とユビキタス言語辞書（`Glossary`）から、次の 2 つの図（Mermaid、または DAG Viewer で読む JSON）を作る。要素は辞書の用語で表す。
  1. **地図 1（Bounded Context のつながり）**: Bounded Context と、Bounded Context をまたぐポリシー（あるコンテキストのイベントが、別のコンテキストのコマンドを起動するもの）だけを表す。
  2. **地図 2（Bounded Context の中のイベントストーミング）**: Bounded Context ごとに、コマンド・ドメインイベント・ポリシーとそのつながりを表す。射影リクエストで求められたときは、全体マップにあるアクター・リードモデル・アグリゲートも足す。既定では足さない。
  - 地図の要素とつながりは、**「壊れている」印の欄**を持つ。印は、仕様全体（業務やワークフローの単位）の矛盾を示すためのものである。初回の実行では印を判定する処理が無いので、欄は常に空である（1.2）。
- **曖昧さの一覧**: FormalTranspiler が曖昧性レポート（`AmbiguityReport`）を返して止まったシナリオについて、決められなかった箇所と、人に確かめる質問の一覧（Markdown）を作る。
- **実装との対応表**: 表示に出す識別子（表示の id）から、内部の識別子と、辞書にある実装の名前と所在を引く表を作る。表示の役割に関係なく作る。
- **表示の役割で、実装の名前を出すかどうかを切り替える**:
  - 役割は `PdM`（既定）と `Eng` の 2 つである。
  - `PdM` では、ファイルのパス・関数名・行番号・コードの断片を出さない。
  - `Eng` では、同じ表示に、実装との対応表と同じ内容（実装の名前と所在）を併記する。本文の文（表示名、意図の候補、論点の文）は役割で変えない。
  - **例外は曖昧さの質問だけである。** 曖昧さの質問は実装の振る舞いについての問いであり、実装の名前を含みうる。そのため `PdM` の曖昧さの一覧には、質問の文と箇所を出さず、シナリオの曖昧さの件数を「エンジニアの確認待ち: N 件」として出す。`Eng` の曖昧さの一覧には、質問・箇所・原文をすべて出す。ほかの項目を役割で変える根拠に、この例外を使ってはならない。
- **検証の状態と論点を、そのまま伝える**:
  - 論点より前に、検証の状態（検査済みか未検証か、行っていない検査、不変条件の検査をしていないこと）を書く。
  - 検証の状態のそばに、**検査の範囲**を書く。検査はシナリオごとに行っており、ほかのシナリオとの矛盾は見ていないことを書く。
  - 論点は、人間の判断の記録があるものだけを決定済みとして表示する。初回の実行では記録が無いので、すべての論点を**未決**と表示する。選択肢は候補として並べ、どれも採択済みとして表示しない（全体仕様 1.5）。
  - 論点カタログが、いまの正本とは別の版から作られたものであれば、そのことを示す。
- **確定の状態を、記録のとおりに表示する**: 用語・意味（資料の節の抜粋）・意図の候補・表示名・質問の文・論点の文は、各モジュールが記録した確定の状態（未生成・候補・確定・要再確認。SpecViewer 仕様 2.4）を持つ。本モジュールは、その状態が分かる形で表示する。確定として記録されていない項目を、確定として表示しない。初回の実行では確定の操作が無いので、すべて「候補」または「未生成」と表示する。
- 曖昧さの出し分け、俯瞰図の 2 階層、検査の範囲、確定の状態は、2026-10-31 に画面の仕様（`spec_viewer.spec.md`）と合わせて足した（中瀬古様 C0AF4DJJK8A 1793382409.578599・1793383559.640939・1793384098.424799）。

### 1.2 扱わないこと (Out of Scope / 禁止事項)
- **テストコードへの変換**: 仕様からテストコード（`test.ts`）を生成する処理は別ツールの責務であり、本モジュールでは取り扱わない（仕様の世界に閉じる）。
- **生成ビューの正本化**: 作ったビューを正本として扱ってはならない（正本は常に形式仕様のみ）。ビューは、いつでも正本から作り直せるものとして扱う。
- **LLM の利用**: 本モジュールは LLM を呼ばない。用語・表示名・意図の候補・論点の文・質問の文は、GlossaryBuilder・IntentSynthesizer・FormalTranspiler・LedgerSynthesizer が記録したものを表示するだけである。
- **未生成の項目を埋めること**: 用語・表示名・意図の候補・論点の文が未生成のときに、実装の名前や定型文で埋めてはならない。未生成であることを、そのまま表示する。
- **辞書の書き換え**: 辞書に項目を足したり、用語を書き換えたりしない。辞書と一致しない実装の名前は、対応表に載せない。
- **壊れた箇所の判定**: 地図の「壊れている」印を判定する処理は、現在の範囲に入らない。
- **人間の判断の受け付け**: 論点に判断を下す画面、候補を確定にする操作、曖昧さの質問への回答と、2 回目以降の実行での表示は、現在の範囲に入らない。言葉とコードの構造の擦り合わせ（インタラクションビューアー）も扱わない。

## 2. 取り扱う情報の定義 (Information Model)

### 2.1 入力情報 (Inputs)
| 入力情報 | 内容 | 必須/任意 |
| :--- | :--- | :--- |
| **形式仕様正本 (`FormalSpec`)** | 唯一の正本である形式仕様。状態変数・命題・操作（条件と書き込みを経路の順に持つ）・表示名を含む | シナリオのビューでは必須 |
| **論点カタログ (`DomainLedgerCatalog`)** | LedgerSynthesizer が作った論点の一覧と検証の状態。初回の実行では、すべての論点が未決である | 任意（無ければ「論点カタログが無い」と表示する） |
| **曖昧性レポート (`AmbiguityReport`)** | FormalTranspiler が決められなかった箇所の一覧と質問の文 | 曖昧さの一覧では必須 |
| **全体マップ (`EventStormingMap`)** | ScenarioExtractor が作ったシステム全体のマップ | 俯瞰図と対応表では必須 |
| **ユビキタス言語辞書 (`Glossary`)** | GlossaryBuilder が作った用語と、用語と実装名の対応 | 俯瞰図と対応表では必須。シナリオのビューでは任意（無ければ、要素の名前を「辞書が無い」と表示する） |
| **意図の候補 (`IntentCatalog`)** | IntentSynthesizer が書いた Bounded Context とシナリオの意図の候補 | 任意（無ければ意図の欄に「意図の候補が無い」と表示する） |
| **射影リクエスト (`ProjectionRequest`)** | 要求する表現形式（仕様書・操作の一覧表・操作の流れ図・曖昧さの一覧、または俯瞰図の階層（地図 1・地図 2）と形式）、地図 2 に足す要素（アクター・リードモデル・アグリゲート。既定は足さない）、表示の役割（`PdM` が既定、`Eng`）、シナリオの表示の id | 必須 |

- **表示の id**:
  - シナリオは切り出しの順に `S-01`、`S-02` …、曖昧さはシナリオの中の順に `S-01-A-001` … とする。これらはパイプライン（オーケストレーター）が振り、射影リクエストで受け取る。
  - Bounded Context は `c1`、`c2` …、コマンド・イベント・ポリシーは `n1`、`n2` … とする。本モジュールが全体マップの並び順に振る。画面でも、地図の要素と用語を指す名前として出す（2026-10-31 中瀬古様 1793382409.578599）。
  - 状態変数は `S-01-V-01` …、論点は `S-01-L-001` … とする。本モジュールがシナリオの中の並び順に振る。論点カタログの論点の識別子（`LEDGER-<シナリオの識別子>-001`）は、シナリオの識別子が実装の所在を含むので、表示に出さない。
  - 本モジュールは内部の識別子を表示に出さない。表示の id は実行ごとに変わりうるので、実行をまたいで項目を指す鍵には使わない。

### 2.2 出力情報 (Outputs)
- **`仕様ビュー成果物 (SpecificationView)`**:
  - 要求された形式の文字列（Markdown、Mermaid、または JSON）と、元にした正本の版（ソースの SHA-256）、元にした論点カタログの報告の識別子、カタログが古いかどうか、表示の役割。
- **`実装との対応表 (ImplementationMap)`**:
  - 表示の id ごとに、内部の識別子、辞書の項目の識別子、実装の名前と所在。状態の変数と条件は、辞書の実装の名前と一致したものだけを載せる。

## 3. 契約仕様 (Design by Contract)

### 3.1 事前条件 (Preconditions)
- 論点カタログを渡すときは、カタログのシナリオが正本のシナリオと同じであること。違うときは、ビューを作らずに契約違反として返す。
- 論点カタログの論点が指す操作が、正本にあること。
- 辞書を渡すときは、辞書が元にした全体マップが、渡した全体マップと同じであること（辞書の `basis`）。違うときは、ビューを作らずに契約違反として返す。
- 表現形式が、1.1 に挙げたもののどれかであること。表示の役割が `PdM` か `Eng` であること。

### 3.2 事後条件 (Postconditions)
- 正本にある状態変数・命題・操作が、すべてビューに現れること（一覧表と流れ図では操作のすべて）。
- 論点カタログにある論点が、すべて仕様書に現れること。曖昧性レポートにある曖昧さが、役割 `Eng` の曖昧さの一覧にすべて現れ、役割 `PdM` の曖昧さの一覧にはその件数が現れること。
- 全体マップにある Bounded Context と、Bounded Context をまたぐポリシーが、すべて地図 1 に現れること。全体マップにあるコマンド・イベント・ポリシーが、所属する Bounded Context の地図 2 にすべて現れること。
- 論点は、人間の判断の記録が無い限り「未決」と表示されていること。意図と、確定の状態を持つ項目は、記録された状態のとおりに表示されていること。
- 検証の状態が「未検証」のときは「未検証」と、その理由と行っていない検査が表示されていること。検査の範囲が表示されていること。「健全」「証明済み」のような、検査の範囲を超える語を使っていないこと。
- 役割 `PdM` のビューに、実装の所在（ファイルのパス・関数名・行番号・形式仕様のソースの `-- @source:` の行）、コードの断片、曖昧さの質問の文と箇所が現れないこと。表示名や用語が未生成の項目以外に、形式仕様の機械的な識別子や全体マップの内部の識別子が現れないこと。
- 役割 `Eng` のビューは、`PdM` のビューと同じ本文に、実装との対応表と同じ内容と、曖昧さの質問・箇所・原文を足したものであること。形式仕様のソース（付録）を載せるのは `Eng` のときだけであること。

### 3.3 不変条件 (Invariants)
- **完全決定論的再現性 (100% Determinism)**: 同一の正本・論点カタログ・曖昧性レポート・全体マップ・辞書・意図の候補・射影リクエストが与えられた場合、いつ何度作っても出力は完全に一致すること（`git diff = 0`）。
- **純粋射影（非破壊性）**: 射影によって正本・論点カタログ・辞書・意図の候補の内容を変えないこと。
- **同じ入力から、どのビューも同じ表示**: どの表現形式でも、同じ項目は同じ表示名・同じ表示の id・同じ状態（未決・未検証・候補など）で表示されること。役割で変わるのは、実装の名前と所在の併記、付録の有無、曖昧さの質問の出し方（1.1 の例外）だけであること。
