# SpecProjector 仕様書

本仕様書は、仕様射影モジュール `SpecProjector` が果たすべき**責務の境界、取り扱う情報の定義、および守るべき契約（事前・事後・不変条件）**を定義する。
本仕様書はプロダクトマネージャー（PdM）やステークホルダーがシステムの振る舞いとして読解・合意可能な形式で記述され、プログラミング言語固有の内部コードには依存しない。

---

## 1. 責務の境界 (Responsibilities & Scope)

### 1.1 担当すること (In Scope)
- **形式仕様正本と論点カタログから、人が読むビューを決定論的に作る**:
  - 正本である形式仕様（`FormalSpec`）と、論点カタログ（`DomainLedgerCatalog`）を入力とし、利用者が指定した表現形式のビュー（Specification View）を作る。
  - 表現形式は次の 3 つである。
    1. **仕様書**: Markdown の文書。シナリオの意図の候補、状態、環境が決める条件、操作ごとの条件と書き込みと結果、検証の状態、論点を、表示名を使って書く。
    2. **操作の一覧表**: 操作ごとに、実行できる条件・結果・状態の変化・関わる論点を並べた表。
    3. **操作の流れ図**: シナリオの起点から、操作ごとの条件と書き込みを経て結果に至る図（Mermaid）。
- **システム全体の俯瞰図**: 全体マップ（`EventStormingMap`）とユビキタス言語辞書（`Glossary`）から、Bounded Context・コマンド・ドメインイベント・ポリシーのつながりの図（Mermaid、または DAG Viewer で読む JSON）を作る。要素は辞書の用語で表す。
- **曖昧さの一覧**: FormalTranspiler が曖昧性レポート（`AmbiguityReport`）を返して止まったシナリオについて、決められなかった箇所と、人に確かめる質問の一覧（Markdown）を作る。
- **実装との対応表**: 表示に出す識別子（表示の id）から、内部の識別子と、辞書にある実装の名前と所在を引く表を作る。表示の役割に関係なく作る。
- **表示の役割で、実装の名前を出すかどうかを切り替える**:
  - 役割は `PdM`（既定）と `Eng` の 2 つである。
  - `PdM` では、ファイルのパス・関数名・行番号・コードの断片を出さない。
  - `Eng` では、同じ表示に、実装との対応表と同じ内容（実装の名前と所在）を併記する。本文の文（表示名、意図の候補、質問、論点の文）は役割で変えない。
- **検証の状態と論点を、そのまま伝える**:
  - 論点より前に、検証の状態（検査済みか未検証か、行っていない検査、不変条件の検査をしていないこと）を書く。
  - 論点は、人間の判断の記録があるものだけを決定済みとして表示する。初回の実行では記録が無いので、すべての論点を**未決**と表示する。選択肢は候補として並べ、どれも採択済みとして表示しない（全体仕様 1.5）。
  - 論点カタログが、いまの正本とは別の版から作られたものであれば、そのことを示す。
  - 意図は候補であることが分かる形で表示し、確定した意図として表示しない。

### 1.2 扱わないこと (Out of Scope / 禁止事項)
- **テストコードへの変換**: 仕様からテストコード（`test.ts`）を生成する処理は別ツールの責務であり、本モジュールでは取り扱わない（仕様の世界に閉じる）。
- **生成ビューの正本化**: 作ったビューを正本として扱ってはならない（正本は常に形式仕様のみ）。ビューは、いつでも正本から作り直せるものとして扱う。
- **LLM の利用**: 本モジュールは LLM を呼ばない。用語・表示名・意図の候補・論点の文・質問の文は、GlossaryBuilder・IntentSynthesizer・FormalTranspiler・LedgerSynthesizer が記録したものを表示するだけである。
- **未生成の項目を埋めること**: 用語・表示名・意図の候補・論点の文が未生成のときに、実装の名前や定型文で埋めてはならない。未生成であることを、そのまま表示する。
- **辞書の書き換え**: 辞書に項目を足したり、用語を書き換えたりしない。辞書と一致しない実装の名前は、対応表に載せない。
- **人間の判断の受け付け**: 論点に判断を下す画面と、2 回目以降の実行での表示は、現在の範囲に入らない。言葉とコードの構造の擦り合わせ（インタラクションビューアー）も扱わない。

## 2. 取り扱う情報の定義 (Information Model)

### 2.1 入力情報 (Inputs)
| 入力情報 | 内容 | 必須/任意 |
| :--- | :--- | :--- |
| **形式仕様正本 (`FormalSpec`)** | 唯一の正本である形式仕様。状態変数・命題・操作（条件と書き込みを経路の順に持つ）・表示名を含む | シナリオのビューでは必須 |
| **論点カタログ (`DomainLedgerCatalog`)** | LedgerSynthesizer が作った論点の一覧と検証の状態。初回の実行では、すべての論点が未決である | 任意（無ければ「論点カタログが無い」と表示する） |
| **曖昧性レポート (`AmbiguityReport`)** | FormalTranspiler が決められなかった箇所の一覧と質問の文 | 曖昧さの一覧では必須 |
| **全体マップ (`EventStormingMap`)** | ScenarioExtractor が作ったシステム全体のマップ | 俯瞰図と対応表では必須 |
| **ユビキタス言語辞書 (`Glossary`)** | GlossaryBuilder が作った用語と、用語と実装名の対応 | 俯瞰図と対応表では必須。シナリオのビューでは任意（無ければ、要素の名前を「辞書が無い」と表示する） |
| **意図の候補 (`IntentCatalog`)** | IntentSynthesizer が書いた Bounded Context とシナリオの意図の候補 | 任意（無ければ意図の欄に「意図の候補が無い」と表示する） |
| **射影リクエスト (`ProjectionRequest`)** | 要求する表現形式（仕様書・操作の一覧表・操作の流れ図・曖昧さの一覧、または俯瞰図の形式）、表示の役割（`PdM` が既定、`Eng`）、シナリオの表示の id | 必須 |

- **表示の id**: シナリオは切り出しの順に `S-01`、`S-02` …、曖昧さはシナリオの中の順に `S-01-A-001` … とする。表示の id を振るのはパイプライン（オーケストレーター）であり、射影リクエストで受け取る。本モジュールは内部の識別子を表示に出さない。

### 2.2 出力情報 (Outputs)
- **`仕様ビュー成果物 (SpecificationView)`**:
  - 要求された形式の文字列（Markdown、Mermaid、または JSON）と、元にした正本の版（ソースの SHA-256）、元にした論点カタログの報告の識別子、カタログが古いかどうか、表示の役割。
- **`実装との対応表 (ImplementationMap)`**:
  - 表示の id ごとに、内部の識別子、辞書の項目の識別子、実装の名前と所在。状態の変数と条件は、辞書の実装の名前と一致したものだけを載せる。

## 3. 契約仕様 (Design by Contract)

### 3.1 事前条件 (Preconditions)
- 論点カタログを渡すときは、カタログのシナリオが正本のシナリオと同じであること。違うときは、ビューを作らずに契約違反として返す。
- 論点カタログの論点が指す操作が、正本にあること。
- 辞書を渡すときは、辞書が元にした全体マップが、渡した全体マップと同じであること（辞書の `basis`）。違うときは、ビューを作らずに契約違反として返す。
- 表現形式が、1.1 に挙げたもののどれかであること。表示の役割が `PdM` か `Eng` であること。

### 3.2 事後条件 (Postconditions)
- 正本にある状態変数・命題・操作が、すべてビューに現れること（一覧表と流れ図では操作のすべて）。
- 論点カタログにある論点が、すべて仕様書に現れること。曖昧性レポートにある曖昧さが、すべて曖昧さの一覧に現れること。
- 全体マップにある Bounded Context・コマンド・イベント・ポリシーが、すべて俯瞰図に現れること。
- 論点は、人間の判断の記録が無い限り「未決」と表示されていること。意図は「候補」と表示されていること。
- 検証の状態が「未検証」のときは「未検証」と、その理由と行っていない検査が表示されていること。「健全」「証明済み」のような、検査の範囲を超える語を使っていないこと。
- 役割 `PdM` のビューに、実装の所在（ファイルのパス・関数名・行番号・形式仕様のソースの `-- @source:` の行）とコードの断片が現れないこと。表示名や用語が未生成の項目以外に、形式仕様の機械的な識別子や全体マップの内部の識別子が現れないこと。
- 役割 `Eng` のビューは、`PdM` のビューと同じ本文に、実装との対応表と同じ内容を足したものであること。形式仕様のソース（付録）を載せるのは `Eng` のときだけであること。

### 3.3 不変条件 (Invariants)
- **完全決定論的再現性 (100% Determinism)**: 同一の正本・論点カタログ・曖昧性レポート・全体マップ・辞書・意図の候補・射影リクエストが与えられた場合、いつ何度作っても出力は完全に一致すること（`git diff = 0`）。
- **純粋射影（非破壊性）**: 射影によって正本・論点カタログ・辞書・意図の候補の内容を変えないこと。
- **同じ入力から、どのビューも同じ表示**: どの表現形式でも、同じ項目は同じ表示名・同じ表示の id・同じ状態（未決・未検証・候補など）で表示されること。役割で変わるのは、実装の名前と所在の併記と、付録の有無だけであること。
