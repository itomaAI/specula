# LedgerSynthesizer 仕様書

本仕様書は、論点合成モジュール `LedgerSynthesizer` が果たすべき**責務の境界、取り扱う情報の定義、および守るべき契約（事前・事後・不変条件）**を定義する。
本仕様書はプロダクトマネージャー（PdM）やステークホルダーがシステムの振る舞いとして読解・合意可能な形式で記述され、プログラミング言語固有の内部コードには依存しない。

---

## 1. 責務の境界 (Responsibilities & Scope)

### 1.1 担当すること (In Scope)
- **検証結果から、人が判断する論点への変換**:
  - 検証結果レポート（機械が見つけた反例と、検証の状態）を入力とし、非専門家（ステークホルダー・意思決定者）が判断できる論点カタログ（`DomainLedgerCatalog`）へ変換する。
  - 各論点を「本来あるべき前提（主張）」「検査で見つかったこと（観測事実）」「人に判断を求める問い（判断質問）」と、反例の種類ごとに決まった 3 つの選択肢として構造化する。主張・観測事実・判断質問の文は LLM が書き、届かなければ「未生成」とする。
- **反例のまとめ方（初回は簡単な形）**:
  - 同じ状態を指す反例を 1 つの論点にまとめ、ほかを従属する反例として記録する。これにより、人は 1 つの状態について 1 回判断すればよい。
  - 状態をまたぐ依存の鎖（ある論点を解消すると別の状態の論点も解消する）は、初回は判定しない。
- **検証の状態を伝える**: 元にした報告が「未検証」なら「未検証」と理由を、「検査済み」で見つかったものが 0 件なら「指定のスコープの中で、行った検査では見つからなかった」と書く。あわせて、行っていない検査（初回の不変条件の検査など）を書く。

### 1.2 扱わないこと (Out of Scope / 禁止事項)
- **仕様の採否の自己決定**: 人に代わって仕様を確定しない。どの選択肢も採択済みとして扱わない（初回の論点はすべて未決）。
- **仕様の確定（ロック）の推奨**: 見つかったものが 0 件でも、仕様を確定する推奨は出さない。初回は不変条件が無く、0 件は仕様が正しいことを示さないためである。
- **機械語の露出**: 形式仕様の識別子や数式記号を、人向けの文に含めない。
- **ソルバ自体の再実行**: 検証は行わない（与えられた検証レポートの解釈・合成に閉じる）。
- **元の記録の書き換え**: 検証結果レポートを書き換えない。

## 2. 取り扱う情報の定義 (Information Model)

### 2.1 入力情報 (Inputs)
| 入力情報 | 内容 | 必須/任意 |
| :--- | :--- | :--- |
| **検証結果レポート (`SolverReport`)** | 検証の状態、実行条件、見つかった反例（未定義遷移・操作の重なり・到達できない操作・デッドロック）と実行列 | 必須 |
| **形式仕様正本 (`FormalSpecification`)** | 表示名、操作、環境の条件の原文を引くための形式仕様 | 必須 |

### 2.2 出力情報 (Outputs)
- **`意思決定論点カタログ (DomainLedgerCatalog)`**（コマンドに 1 つ）:
  - **要約の範囲**: 元にした `SolverReport` の識別子と実行条件、形式仕様正本の版、元の記録の反例の件数 N、まとめた論点の件数 k。
  - **検証の状態**: 「検査済み」か「未検証」と理由、実行しなかった検査、行っていない不変条件の検査、反例を 1 件だけ返す検査。
  - **論点の一覧**（各論点に次を持つ）:
    - **論点ID**: 一意な識別子（例: `LEDGER-<コマンド>-001`）
    - **種類**: 未定義遷移・操作の重なり・到達できない操作・デッドロックのどれか
    - **主張・観測事実・判断質問**: LLM が書いた文と、その確定の状態（未生成・候補・確定・要再確認。SpecViewer 仕様 2.4）。届かなければ「未生成」、書けたときは「候補」。本モジュールが「確定」にすることはない。文の確定の状態は、論点の「決定」（人間が選択肢を選んだ記録）とは別の欄である
    - **実行列**: その状況に至る最短の実行列（到達できない操作には無い）
    - **選択肢**: 種類ごとに決まった 3 つ（例: 未定義遷移なら「扱いを仕様として決める」「実装の誤りとして直す」「実際には起きないとして認める」）
    - **従属する反例**: 同じ状態を指し、この論点にまとめた反例（元の記録の中の位置で示す）
    - **決定**: 初回は常に未決。2 回目以降、人が選んだ選択肢と中身を入れる欄

## 3. 契約仕様 (Design by Contract)

### 3.1 事前条件 (Preconditions)
- `SolverReport` と `FormalSpecification` の対象のコマンドが一致し、報告が元にした形式仕様正本の版が入力の形式仕様正本と一致していること。満たしていない場合は契約違反として止まる。

### 3.2 事後条件 (Postconditions)
- レポートに含まれるすべての反例が、いずれかの論点から**たどれる**こと。論点の本体であるか、論点に従属する反例であるかのどちらかである（N ＝ 論点の本体の数 ＋ 従属する反例の数）。
- 各論点に、反例の種類に応じた 3 つの選択肢があること。主張・観測事実・判断質問は、LLM の文か「未生成」のどちらかであり、定型文で埋めないこと。
- カタログに**要約の範囲**と**検証の状態**が記録されていること（2.2 を参照）。
- 「未検証」の報告から作ったカタログを、見つかったものが無かったカタログとして扱わないこと。

### 3.3 不変条件 (Invariants)
- **推測排除の中立性**: システム自身が勝手な推測で仕様の穴を埋めず、必ず「未決の論点」として中立に人間に問うこと。
- **論点の構成の決定論性**: 同じ報告と形式仕様正本からは、同じ論点の数・まとめ方・識別子・選択肢・並びになること。LLM の文は記録して再利用する（全体設計 1.3）。

### 3.4 元の記録と要約の関係
- `SolverReport` は元の記録、`DomainLedgerCatalog` はその要約（コピー）である。「漏れなく」の約束は元の記録に課され、本モジュールは「どこまでを、どうまとめたか」を示すことで整合を保つ（Loom で文脈を畳むときに「… まで／N 件」を書くのと同じ流儀）。
- 本モジュールは元の記録を書き換えない。
- 形式仕様正本が更新されたら、古い `SolverReport` から作ったカタログは古いと示し、再検証を促す。人間がすでに合意した論点の結果は、その印によって消えたり上書きされたりしない（全体アーキテクチャ 4.3 の「決定事項の不破壊性」）。
