# SpecViewer 基本設計書

本設計書は、画面モジュールの仕様書（`spec_viewer.spec.md`）に規定された、1 回の実行の出力を閲覧の画面として見せる処理を、全体基本設計書（`system_solution.design.md`）の規約に準拠して**どのように技術的・構造的に実現するか（How）**を定義する。

---

## 1. アーキテクチャと全体設計制約の継承

### 1.1 全体設計制約の適用
- **2 つに分ける**: 出力のファイルから画面の中間表現（ビューモデル）を作る部分と、ビューモデルを画面に描く部分に分ける。
  - **ビューモデルを作る部分**: `specula/src/viewer/`（Pure ESM, Target: ES2022+）。ファイルの読み書きも画面の操作もしない（Zero-I/O Core）。出力のファイルの中身（パース済みの JSON と、Markdown・Mermaid の文字列）と表示の役割を受け取り、画面ごとのビューモデルを返す。参照するのは `src/types/` と、SpecProjector の表示の純粋な関数（`src/core/m5/` の `labels.ts`・`view_model.ts` のうち、I/O を持たない文の組み立て）だけとする。SpecProjector と同じ項目を同じ文で出すため（仕様 3.3）、文を組み立てる処理を写し直さない（6.5）。
  - **画面に描く部分**: 起動アプリ（Itera OS の app）。出力先のファイルを `FileSystemPort` で読み、ビューモデルを作る部分を呼び、結果を描く。表示の判定（役割による出し分け、未決・未検証・候補の判定）を描く側に書かない。
- **分ける理由**: 役割による出し分けと状態の判定を、テストのできる純粋な関数に閉じ込めるためである。描く側に判定を書くと、画面ごとに表示が食い違い、仕様 3.3 の「同じ項目は同じ表示」をテストで確かめられない。
- **LLM を使わない**: ビューモデルは決定論的に作る（全体設計 1.2）。
- **書き込まない**: 出力先に書き込まない（仕様 1.2）。画面の状態（開いているタブ、絞り込み）はファイルに残さない。

### 1.2 公開する関数
```typescript
buildRunView(
  outputs: RunOutputs,            // 出力先から読んだファイルの中身（2 節）
  viewRole: "PdM" | "Eng",
): RunView;                       // 4 つの画面とシナリオの詳細のビューモデル（リンクは表示の id で張る。6.11）

checkRunOutputs(outputs: RunOutputs): RunOutputsCheck;   // 仕様 3.1 の事前条件
```
- `checkRunOutputs` が事前条件の破れを返したときは、起動アプリは画面を作らずに理由を表示する。
- ビューモデルの型の詳細は、画面を実装するときに決めて 6 節に書く。

### 3.1 シナリオ一覧

### 3.4 全体地図
- **地図 1**: Bounded Context の箱と、またぐポリシーの矢印。箱を選ぶと、用語・意図の候補（確定の状態の印）・属するシナリオの数をポップアップで出し、地図 2 と、その Bounded Context で絞り込んだシナリオ一覧へのリンクを置く。Bounded Context が 1 つだけのときは、全体地図を開いたら地図 2 を出す。
- **地図 2**: 既定はコマンド・ドメインイベント・ポリシーとそのつながり。切り替えで、アクター・リードモデル・アグリゲートを足す。切り替えは SpecProjector に地図 2 を作り直させるのではなく、SpecProjector が出した地図 2 の JSON（足す要素を含む版）の表示を切り替える。
- 要素は用語と表示の id（`c1`・`n1`）で表す。用語が未生成の要素は「〈種類〉 〈番号〉（名前は未生成）」（SpecProjector 基本設計 8.2）。
- 要素を選んだときのポップアップ: 用語、確定の状態、意味（資料の抜粋）、その要素を起点にしたシナリオ。1 つのコマンドがイベントを複数発生させるとシナリオはイベントごとに分かれるので（ScenarioExtractor 仕様 2.2）、シナリオが複数あるときは一覧から選ぶ。
- 壊れた箇所の印: 地図の JSON の印の欄が空でなければ、要素とつながりに印を描く。初回は欄が常に空である。
- 実装の名前と所在（Eng のみ）。

## 6. 実装のときに決めたこと
2026-10-31 に決めた。画面ごとのビューモデルの型は、その画面を実装するときにこの節へ足す。

### 6.1 出力先の読み方（`RunOutputs`）
- 読むのは `src/lib/read_outputs.ts` の `readRunOutputs(fs: FileSystemPort, outDir: string): Promise<RunOutputs>` とする。ファイルを読むので `src/viewer/` には置かず、書く側の `src/lib/write_outputs.ts` と対にする。
- 読むファイルは 2 節の表のものだけである。`system_map.mmd`、シナリオごとの `solver_report.json`・`ambiguity.md` は画面で使わないので読まない。
  - 2026-10-31（PR #31）の時点では「`spec.json` も使わないので読まない」としていたが、誤りだった。論点の関わる操作・実行列の値・実行しなかった検査の名前は、SpecProjector が `spec.json`（`FormalSpecification`）の表示名から文にしている（`view_model.ts` の `verificationView`・`issueView`）。同じ文を出すには `spec.json` が要るので、読むファイルに足した（6.5）。
- シナリオのディレクトリは、`run_report.json` の `scenarios` から `scenarios/<safeName(scenarioId)>/` として引く。`FileSystemPort.list` は順序を保証しないので、ディレクトリの一覧からは引かない。読むファイルはシナリオの `kind` で決める（`COMPLETED`: `spec.json`・`spec.md`・`matrix.md`・`flow.mmd`・`spec.als`・`ledger.json`、`AMBIGUOUS`: `ambiguity.json`、`STOPPED`: なし）。`run_report.json` が無いか読めないときは、シナリオのファイルを読まない。
- ファイルごとの結果は、次の 3 通りのどれかで持つ。読めなかったことを `null` 1 つにまとめないのは、無いのか壊れているのかで表示する理由が違うためである。
  - `{ kind: "OK", value }`: JSON はパースした値、Markdown・Mermaid・Alloy は文字列。
  - `{ kind: "MISSING" }`: ファイルが無い。
  - `{ kind: "INVALID", reason }`: JSON としてパースできない。
- `readRunOutputs` は形の検査をしない（JSON のパースだけ）。形と組み合わせの検査は `checkRunOutputs` で行う。

### 6.2 事前条件の検査（`checkRunOutputs`）
- 返すのは `{ ok: boolean; problems: RunOutputsProblem[] }` とする。`ok` が `false` のとき、起動アプリは画面を作らずに `problems` を表示する（1.2）。
- 画面を作れないもの（`ok` を `false` にするもの）:
  - `run_report.json` が無いか、読めない。
  - 読めた JSON のファイルが壊れている（`INVALID`）。
  - `basis` を持たない（`basis` を足す前の古い出力）。
  - `run_report.json`・`glossary.json`・`intents.json`・`implementation_map.json`・`system_map.json` のうち、あるものどうしの `basis`（`mapHash`・`documentsHash`）が一致しない（仕様 3.1）。
  - `run_report.json` のシナリオの `kind` から決まるシナリオのファイルが無い（同じ実行の書き出しなら必ずあるため）。
- 画面を作れるもの（`problems` に入れない）: 仕様 2.1 で任意とされている `glossary.json`・`intents.json`・`implementation_map.json`・`system_map.json` が無いこと。どの画面で何を出すかは `buildRunView` が決める（例: 辞書が無ければ要素の名前を「辞書が無い」と表示する。全体地図は俯瞰図が無ければ理由を出す）。
- 表示の役割と `system_map.json` の `viewRole` の関係は、6.4 が決まるまで検査しない。

### 6.3 ビューモデルの型の方針
- 型は `src/viewer/types.ts` に置き、`src/types/` と、SpecProjector の表示の型（`src/core/m5/view_model.ts` の `VerificationView`・`IssueView`）だけを参照する。SpecProjector と同じ項目は同じ型で持ち、写し直さない（1.1）。
- 確定の状態の印は、SpecProjector と同じく文の後ろに足した文字列で持つ（`statusMark`。6.5）。描く側は文をそのまま出し、状態を判定しない（1.1）。2026-10-31 の PR #31 の時点では「本文の文と確定の状態は組で持ち、描く側が印を付ける」としていたが、SpecProjector の文（`IssueView` など）を使うと印は文に入っているので、こちらに合わせた。
- 画面どうしのリンクの鍵（内部の識別子）は、ビューモデルの中のリンクの表だけに置き、描く文字列には入れない（4 節）。

### 6.4 画面の描き方
- **依存を足さない**: Itera OS が配布する外部ライブラリ（`MetaOS.vendor`）は MathJax・Monaco・pdf.js・pdf-lib で、Mermaid と Markdown の描画のライブラリは無い。そのため、出力を描く処理を自分で書く。範囲は SpecProjector が出すものに限る。
  - **Markdown**（`spec.md`・`matrix.md`）: SpecProjector が出す記法（`render_document.ts`・`render_matrix.ts` の見出し・段落・箇条書き・番号付きの箇条書き・表・引用・コードブロック）だけを、ブロックの木に分ける純粋な関数を `src/viewer/` に置く。
    - 行の中の書式（強調・インラインのコードなど）は解釈せず、文字のまま出す。SpecProjector は行の中の書式を出さず、LLM の文は改行を空白にするだけで Markdown の記号を逃がしていない（`escape.ts` の `mdLine`）ため、解釈すると LLM の文の記号が書式に化ける。
    - 表のセルの `\|` は `|` に戻す（`mdCell`）。コードブロックの囲みは 3 つ以上のバッククォートで、長さはソースによって変わる（`fenceFor`）。
  - **地図と流れ図**: 地図は `system_map.json` から、流れ図は `flow.mmd`（SpecProjector の流れ図が出す範囲の flowchart）から、ノードとつながりのグラフを作り、層に並べる純粋な配置の関数を `src/viewer/` に置く。描く側は配置の結果を SVG にするだけにする。
- **LLM の文は `textContent` で描く**: 用語・意図・論点の文・質問の文は LLM が作り、LLM は解析対象のコードと資料を読んでいる。そのため、`innerHTML` に入れず、文字列として描く。
- **表示の役割の切り替え**: 今の出力は、利用者向けのビュー（仕様書・操作の一覧表・流れ図・曖昧さの一覧・俯瞰図）を 1 つの役割で書く。仕様 1.1 の「Global Menu で役割を切り替える」を満たすには、出力の役割に固定するか、両方の役割のビューを書き出すかを決める必要がある。中瀬古様の答えを待っている（2026-10-31）。

### 6.5 シナリオ一覧とシナリオの詳細
- **SpecProjector の文を使う**: 検証の状態は SpecProjector の `verificationView`（1 行目と箇条書きの文）で、論点は `issueGroupsOf`（見出しごとの組。論点の 3 つの文と確定の状態の印、関わる操作、実行列、選択肢、従属する反例の数）で作る。LLM の文は `llmText`、確定の状態の印は `statusMark`、未検証の理由は `UNVERIFIED_REASON_TEXT`、曖昧さの種類は `AMBIGUITY_KIND_TEXT`（`render_ambiguities.ts`）を使う。
  - そのために `view_model.ts` から `verificationView`・`UNVERIFIED_REASON_TEXT` を export し、`buildViewModel` の中にあった論点の番号の振り方と見出しの組み分けを `issueDisplayIds`・`issueGroupsOf` に切り出して export した（`buildViewModel` はこれを呼ぶ。振る舞いは変えていない）。どれも引数から文を作るだけで I/O を持たない。
- **`buildViewModel` は使わない**: `buildViewModel` は `ProjectionContext.scenario`（`ScenarioTarget`）を受け取るが、出力には `ScenarioTarget` が無い。実行の報告の行から `ScenarioTarget` を作り直すと、出力に無い値（起点の識別子など）を推測で埋めることになるため、使わない。
- **論点の表示の id**: `buildViewModel` と同じく、`ledger.json` の `issues` の並びで `S-01-L-001` … を振る（SpecProjector 基本設計 8.7）。
- **シナリオの名前の引き方**: SpecProjector は起点の識別子で辞書を引くが（`titleOf`）、実行の報告の行には起点の識別子が無い。画面は `implementation_map.json` の `SCENARIO` の行（`displayId` が一致するもの）の `glossaryEntryId` で `glossary.json` の項目を引く。項目の種類が行の `inletType` と同じで、用語が生成されているときだけ名前にする。題の形は `titleOf` と同じ「`S-01 〈表示名〉〈確定の状態の印〉`」とする。
  - 名前を出せないときは、理由を分けて書く。`implementation_map.json` が無い:「（名前を引けない: 実装との対応表が無い）」。`glossary.json` が無い:「（名前を引けない: 辞書が無い）」。項目が無い・種類が違う・用語が未生成:「（名前は未生成）」（SpecProjector と同じ）。対応表や辞書が無いことを「未生成」と書くと、事実と違うためである。
- **意図の候補**: `intents.json` の `scenarios` を `scenarioId` で引き、`llmText` の文に `statusMark(intentStatus)` を足す（SpecProjector の仕様書と同じ）。`intents.json` が無いか、そのシナリオの候補が無ければ「意図の候補が無い」と書く。
- **Bounded Context と期待イベント**: 実行の報告の行の `boundedContext`・`expectedEvent` は全体マップの識別子なので、そのまま出さない。辞書の項目（種類が `BOUNDED_CONTEXT`・`EVENT` で id が一致するもの）の表示名に確定の状態の印を足して出す。引けないときはシナリオの名前と同じ規則で理由を書く。
- **起点の種類・アクター・画面のルート**: 起点の種類は `COMMAND` を「操作」、`POLICY` を「反応」と書く。アクターは `actor.name` を出す。画面のルートは `null` なら出さない。
  - アクターの名前は認可のコードから拾った役割の名前で、辞書の用語が無い。PdM に出してよいかは確かめている（2026-10-31）。
- **シナリオの表の文**: 検証の列は、仕様になったシナリオだけ「論点が見つかった」「指定の範囲で、行った検査では見つからなかった」「未検証（理由）」と書く。件数の列は「論点 N 件」、曖昧さで止まったシナリオは `PdM` で「エンジニアの確認待ち: N 件」、`Eng` で「曖昧さ N 件」。途中で止まったシナリオは件数を出さない。
- **タブの代わりに出す文**: 曖昧さで止まったシナリオは 3.2 の文。途中で止まったシナリオは「このシナリオは途中で止まったため、仕様にならなかった。」とし、`Eng` では止まった段とエラーの名前を足す。
- **起点の所在（Eng のみ）**: 対応表の `SCENARIO` の行の `implementation.locations` を、文字列にせずそのまま持つ。`PdM` では持たない（`null`）。
- **公開する関数**: `buildScenarioList(outputs, viewRole)` と `buildScenarioDetails(outputs, viewRole)`（`src/viewer/scenarios.ts`）。どちらも `checkRunOutputs` を通った入力を受け取り、通っていない入力では例外を投げる。1.2 の `buildRunView` は、4 つの画面がそろった段階でこれらを束ねる。

### 6.6 詳細のタブ（仕様書・操作の一覧表・形式仕様のソース）
- **Markdown をブロックの木に分ける**: `src/viewer/markdown.ts` の `parseMarkdown(text)` が、`spec.md`・`matrix.md` を見出し・段落・箇条書き・番号付きの箇条書き・表・引用・コードブロックのブロックの並びに分ける。描く側はブロックを要素にし、文字列は `textContent` で入れる（6.4）。
- **行の先頭の記号だけで分ける**: SpecProjector は、LLM の文を必ず決まった前置きの後ろに置く（「- 主張: 」「### 」、表のセル、「1. 条件: 」など）。段落の行は固定の文である。また、LLM の文の改行は空白にしてある（`mdLine`・`mdCell`）。そのため、行の先頭の記号で種類を決めれば、LLM の文がブロックの区切りに化けることはない。判定の順は、コードブロックの囲み（3 つ以上のバッククォート。同じ長さの囲みの行で閉じる）→ 見出し（`#` 1〜6 個と空白）→ 表（`|` で始まり、2 行目が区切りの行）→ 引用（`> `）→ 箇条書き（`- `）→ 番号付き（数字と `. `）→ 空行 → 段落とする。
- **表のセル**: 前後の `|` を外し、`\` の付かない `|` で分け、`\|` を `|` に戻して前後の空白を取る（`mdCell` の逆）。区切りの行が無い `|` の行は段落として扱う。
- **行の中の書式は解釈しない**（6.4）。Eng の題に付く所在の併記（`markdownImplementationNote` のバッククォート）も、文字のまま出す。
- **形式仕様のソースのタブ**: `Eng` のときだけ、`spec.als` から `-- @source:` の行を除いたもの（`stripSourceComments`。SpecProjector の付録と同じ）を持つ。`PdM` では `null`。
- **役割との関係**: `spec.md`・`matrix.md` は出力を作ったときの役割で書かれている（6.4 の表示の役割の切り替え）。`Eng` で書いた `spec.md` には付録（形式仕様のソース）が入るので、画面の役割が `PdM` でも、そのまま出すと付録が見える。切り替えの答え（A/B）が出るまで、仕様書のタブは書かれた `spec.md` をそのまま木にする。

### 6.7 仕様不備一覧
- **公開する関数**: `buildIssueList(outputs, viewRole)`（`src/viewer/issues.ts`）。`checkRunOutputs` を通った入力を受け取り、通っていない入力では例外を投げる（6.5 と同じ）。
- **論点**: 仕様になったシナリオのうち、論点が 1 件以上あるものを実行の報告の順に並べる。中身は `issueGroupsOf` の見出しごとの組（6.5 のシナリオの詳細と同じ値）で、表示の id は `issueDisplayIds` で振る。既定の並べ方（3.3「シナリオごとにまとめ、見出しに件数」）に合わせ、シナリオごとに `issueCount` を持つ。
- **論点から操作の一覧表の行へのリンク**: 論点カタログの `operations`（形式仕様の操作の識別子）を、`spec.json` の `operations` の中の位置に直して持つ（`operationRows`。論点の表示の id から行の位置の配列）。操作の一覧表の行は、形式仕様の操作の順に並ぶため（`render_matrix.ts`）。描く側は、詳細の操作の一覧表のブロックの表の行をこの位置で指す。
- **曖昧さ**: 曖昧さで止まったシナリオを実行の報告の順に並べる。件数は実行の報告の行の `counts` の合計で、文はシナリオ一覧と同じ（`PdM`「エンジニアの確認待ち: N 件」、`Eng`「曖昧さ N 件」）。
  - `PdM` では質問・箇所・原文を持たない（`items` が `null`）。質問は実装の振る舞いについての問いで、実装の名前を含みうるため（SpecProjector の曖昧さの一覧と同じ理由）。
  - `Eng` では、SpecProjector の曖昧さの一覧（`render_ambiguities.ts`）と同じく、`ambiguity.json` の `issues` の並びで `S-02-A-001` … と振り、種類の文（`AMBIGUITY_KIND_TEXT`）、質問の文と確定の状態の印、所在（ファイルと行）、原文（末尾の改行を除く）を持つ。`unitIds` は持たない。
- **途中で止まったシナリオ**: 論点も曖昧さも持たないので出さない。
- **リンクの鍵は表示の id にする**: 4 節は「鍵は内部の識別子」としていたが、ビューモデルは内部の識別子を持たず、シナリオ・論点・曖昧さを表示の id（`S-01`・`S-01-L-001`・`S-02-A-001`）で指す（シナリオ一覧と詳細も同じ。6.5）。表示の id は 1 回の実行の中で一意なので、リンクの鍵に使える。内部の識別子を描く側へ渡さないので、URL やアドレスバーに漏れることもない（4 節の後半の約束）。
- **絞り込み**: 種類・シナリオ・論点の種類・曖昧さの種類（3.3）で絞る処理は描く側で行う。ビューモデルの値（`displayId`・`IssueGroupView.kind`・`AmbiguityItemView.kind`）だけで絞れるため、絞り込み用の値は足さない。

### 6.8 用語辞典
- **公開する関数**: `buildGlossaryView(outputs, viewRole)`（`src/viewer/glossary.ts`）。`checkRunOutputs` を通った入力を受け取り、通っていない入力では例外を投げる（6.5 と同じ）。出すのは提示する項目（Bounded Context・コマンド・イベント・ポリシー）だけで、記録だけの項目は出さない（GlossaryBuilder 仕様 1.2）。
- **表示の id の引き方**: 俯瞰図の JSON（`system_map.json`）のノードは表示の id（`c1`・`n1`）を持つが、辞書の項目の id を持たない（`render_system.ts` の `renderSystemJson`）。そのため、`implementation_map.json` の `BOUNDED_CONTEXT`・`COMMAND`・`EVENT`・`POLICY` の行の `glossaryEntryId` で引く。対応表は俯瞰図と同じ順で番号を振る（`implementation_map.ts` の先頭のコメント。`c` は全体マップの Bounded Context の順、`n` はイベント・コマンド・ポリシーの順）。シナリオの名前の引き方（6.5）と同じ表を使う。
  - 対応表が無いときは表示の id を `null` にし、一覧の上に「表示の id を引けない: 実装との対応表が無い」を出す。並びは辞書の順（項目の id の辞書順）にする。対応表で番号を引けない項目が 1 つでもあるときも、辞書の順にする（番号のある項目と無い項目を混ぜて並べないため）。
- **区切り**: Bounded Context ごとに、その Bounded Context の項目を先頭に置き、所属する項目（`contextId`）と、そこへまたいでくるポリシー（`crossesTo`）を続ける。またぐポリシーは両方の区切りに出し、所属の側では「〈Bounded Context〉へまたぐ」、またいだ先の側では「〈Bounded Context〉からまたいでくる」と書く。所属を持たない項目（全体マップのポリシー）は、最後の「所属する Bounded Context が無い」の区切りに置く。区切りを出すのは、Bounded Context が 2 つ以上あるか、所属の無い区切りがあるときだけ（3.5）。
  - Bounded Context の名前は用語の文で、用語が無ければ俯瞰図と同じく「Bounded Context c1（名前は未生成）」とする。
- **項目の文**: 用語は 6.5 の名前と同じ形（`labelOfEntry`。表示名と確定の状態の印、未生成なら「（名前は未生成）」）。種類の文は俯瞰図（`render_system.ts` の `KIND_TEXT`）に合わせて「Bounded Context」「コマンド」「イベント」「ポリシー」とする（3.5 の表の「ドメインイベント」は、同じ要素を画面ごとに違う語で呼ばないよう「イベント」にした）。意味は抜粋の本文に確定の状態の印を足し、上限で切ったかを `meaningTruncated` で持つ。抜粋が無ければ「資料に記述が無い」。
- **確定の状態の説明**: `statusMark` は候補に印を付けない（`labels.ts`）。SpecProjector の仕様書が冒頭に説明を 1 回だけ書くのと同じく（`render_document.ts`）、用語辞典も一覧の上に 1 回だけ説明の文（`statusNote`）を出す。絞り込み用に、項目ごとの `termStatus` も持つ。
- **用語の出どころ**: 節の識別子（`<資料のパス>#<見出しの並び>`、GlossaryBuilder 設計 2 節）を資料と見出しに分ける（`sourceOf`）。資料のパスに `#` があっても誤らないよう、辞書の `documents` の `read`・`truncated` のうち最も長く一致するパスで分け、一致しなければ最初の `#` で分ける。
- **資料とコードのずれ**: 辞書の `gaps` を、表示の id と用語の文に直して持つ（内部の識別子を描く側へ渡さない。4 節）。項目に対応しない資料の名前は、`IMPLEMENTATION` のときだけ件数と開いたときの一覧を持ち、`BUSINESS` では `null` にする（3.5。資料のインラインコードの名前は実装の側の情報のため。Q8）。
- **意味のコードのパス**: `BUSINESS` のときは、意味（資料の抜粋）の中で資料が書いたコードのパス（区切りに `src/` を含むもの）を「（コードのパス）」に置き換える（`hideSourcePaths`。Q6）。パスを含むインラインコードは囲みごと置き換え、関数名だけのインラインコードは残す。`IMPLEMENTATION` では抜粋をそのまま出す。辞書の `excerpt` は書き換えない（画面の側だけで置き換える）。
- **実装の名前と所在**: `Eng` のときだけ、辞書の項目の `implementation` を写して持つ。`PdM` では `null`。
- **用語辞典から地図 2 へのリンク**（4 節）: 項目の表示の id が俯瞰図の要素の id と同じなので、描く側はそれで地図 2 の要素を指す。どの地図 2 に出るかは、`system_map.json` の `details` のノードで描く側が引く。

### 6.9 流れ図のグラフと層の配置
- **公開する関数**: `src/viewer/graph.ts` の `parseFlow(text)`（`flow.mmd` をグラフに戻す）、`layoutLayers(nodeCount, edges)`（層に並べる）、`buildFlowView(text)`（その 2 つを続けて行う）。シナリオの詳細の流れ図のタブ（`ScenarioTabsView.flow`）は `buildFlowView` で作る。全体地図（3.4）も同じ `layoutLayers` で並べる。
- **読む範囲**: `render_flow.ts` が出す行だけを読む。1 行目の「flowchart TD」、「%%」の注意の行（論点カタログが古いとき）、ノード `id["文"]`、つながり `a --> b`、空行である。ノードの識別子の形も `render_flow.ts` の振り方（起点の `s`、操作ごとに `_0`・`_1` …・`_r`）に限る。それ以外の行があれば、画面を作るのをやめずに、流れ図のタブだけを「流れ図の N 行目を読めない」の理由にする（`UNREADABLE`）。読み方を推測で広げると、SpecProjector の流れ図の書き方が変わったときに、違う図を黙って出すためである。
- **ノードの指し方**: ノードとつながりは並びの位置（0 から）で指す。`flow.mmd` のノードの識別子は形式仕様の操作の識別子（`op1` など）を含むので、ビューモデルにも読めない理由の文にも入れない（4 節、SpecProjector 基本設計 3.2）。ノードの種類（起点・操作・条件と書き込み・結果）は識別子の形から決めて持つ。
- **文の戻し方**: `mermaidLabel`（`escape.ts`）の `#quot;`・`#lt;`・`#gt;` を、1 回の置き換えで `"`・`<`・`>` に戻す。限界が 2 つある。`mermaidLabel` は `#` を逃がさないので、文にもともと「#quot;」と書いてあれば `"` に戻る。改行は空白にされているので戻せない。どちらも SpecProjector の側で逃がし方を変えないと直せないので、画面の側では補わない（仕様 1.2）。
- **層の配置**（決定論的。同じ入力から必ず同じ配置になる）:
  1. 閉路を切る。ノードの並びの順に深さ優先でたどり、たどっている途中のノードへ戻るつながりを、下から上へ向かうもの（`reversed`）とする。流れ図には閉路が無いが、全体地図にはポリシーとコマンドの間で閉路がありうるため、同じ関数で扱う。自分へのつながりは層を決めるのに使わない。
  2. 層を決める。各ノードを、上の層から届く最も長い道の長さの層に置く。そのため、`reversed` でないつながりは、必ず上の層から下の層へ向かう。
  3. 層の中の並びを決める。上の層から順に、つながりの元の並びの位置の平均で並べ、つながりの元が無いノードは後ろに置く。値が同じなら、ノードの並びの順にする。
  - 層をまたぐつながりに中継の点を置かない。描く側は端どうしを結ぶ。交差を減らす並べ替えを何度も繰り返す方法は採らない。流れ図は起点から操作ごとに 1 本の道になるので、1 回の並べ方で交差しないためである。全体地図で交差が読みにくければ、PR 4b で見直す。
- **座標を持たない**: 配置は層と並びの位置だけを返し、画素の座標は描く側が決める。ノードの幅は文字の大きさと書体で変わり、純粋な関数では分からないためである。

### 6.10 全体地図
- **公開する関数**: `buildMapView(outputs, viewRole)`（`src/viewer/map.ts`）。`checkRunOutputs` を通った入力を受け取り、通っていない入力では例外を投げる（6.5 と同じ）。
- **元にするもの**: `system_map.json`（`SystemMapBundle`）の `contextMap`（地図 1）と、`details` の Bounded Context ごとの `core`・`supporting`（地図 2）。要素の文は JSON の `label` をそのまま使う（SpecProjector の俯瞰図と同じ文。種類の前置きが入っている）。俯瞰図が無ければ「全体地図を出せない: 俯瞰図が無い」の理由だけを持つ（仕様 2.1 で任意のため）。
- **JSON の欄を確かめて読む**: `SystemMapJson` のノードとつながりは型の上では `Record<string, unknown>` なので、使う欄（`id`・`kind`・`label`・`crossing`・`broken`・`implementation`、つながりの `from`・`to`・`kind`・`policy`・`label`・`broken`）の型を確かめてから読む。形が違えば、全体地図だけを「俯瞰図の形が違う（〈場所〉: 〈欄〉）」の理由にする（画面全体は止めない。6.9 と同じ考え方）。場所は地図の番号と並びの位置、表示の id だけで書く。
  - 確かめること: id は Bounded Context なら `c`、ほかは `n` で始まる番号。kind は俯瞰図の種類。つながりは同じ地図のノードを指す。地図 1 のつながりはまたぐポリシー（`kind` が `POLICY` で `policy` と `label` を持つ）だけ。地図 2 は先頭が `context` の Bounded Context で、2 つ目の Bounded Context を持たない。地図 2 は地図 1 の Bounded Context ごとに 1 つずつある（全体設計 4.1）。並びが地図 1 と違うときは形の違いにせず、地図 1 の並びに並べ替えて読む。地図 2 が足りない・同じ Bounded Context が 2 つある・地図 1 に無い Bounded Context があるときは形の違いにする。
  - JSON のノードの `intent`（意図の候補の文）は使わない。確定の状態の印が無いので、意図の候補は `intents.json` から作る（下のポップアップ）。
- **つながりの文**: 地図 2 は俯瞰図の Mermaid と同じ文（「発生させる」など）にするため、`render_system.ts` の `EDGE_TEXT` を export して使う。地図 1 はまたぐポリシーの文（JSON の `label`）を使い、そのポリシーの表示の id（`policy`）を持つ。
- **配置**: 地図 1・地図 2 とも、ノードとつながりを並びの位置に直し、6.9 の `layoutLayers` で層に並べる。地図 2 の `core` と `supporting` は別々に並べ、描く側が切り替える（3.4）。地図 2 の Bounded Context のノード（JSON の先頭）は、箱の題として別に持ち、層には入れない。
- **ポップアップ**: 要素の用語・確定の状態・意味は、用語辞典のビューモデル（6.8 の `GlossaryEntryView`）を表示の id で引いて使う。同じ文を 2 か所で作らないためである。アクター・リードモデル・アグリゲートは辞書の項目を持たないので、JSON の文だけを出す。
  - またぐポリシーは用語辞典の 2 つの区切りに違うまたぎの文で出るので、ポップアップの項目では `crossing` を `null` にし、またぎは要素の `crossing`（表示の id の組）で持つ。
  - 項目を引けないときは理由（`entryNote`）を書く。辞書が無い:「用語と意味を出せない: 辞書が無い」。対応表が無い:「用語と意味を引けない: 実装との対応表が無い」。対応表はあるが引けない（対応表に行が無いか、辞書に項目が無い）:「用語と意味を引けない: 辞書に項目が無い」。
  - 辞書の項目の id は、対応表の行の `glossaryEntryId` を表示の id から逆に引いて得る（`glossary.ts` の `displayIdsOf` を export して使う）。引けないときは、意図の候補・シナリオの数・起点のシナリオを出さず、理由（`lookupNote`。「〜を引けない: 実装との対応表が無い」「〜に行が無い」）を書く。
  - Bounded Context の箱には、意図の候補（`intents.json` の文と確定の状態の印。用語辞典と同じく表示の id から辞書の項目を引いて探す）と、属するシナリオの数（実行の報告の行の `boundedContext`）を持つ。
  - コマンドとポリシーには、その要素を起点にしたシナリオの表示の id の一覧を持つ（対応表の `SCENARIO` の行の `glossaryEntryId` が起点の辞書の項目。6.5）。対応表が無ければ一覧を出さず、理由を書く。
- **Bounded Context が 1 つ**のときは、`startWithDetail` を `true` にする（描く側は地図 2 から開く。3.4）。
- **表示の役割**: 実装の名前と所在は、画面の役割が `Eng` で、JSON に `implementation` があるときだけ持つ。JSON は出力を作ったときの役割で書かれているので（6.4）、画面の役割が `PdM` なら JSON にあっても持たない。
- **壊れた印**: ノードとつながりの `broken` が `null` でなければ、印を描くための `broken: true` を持つ。初回は常に `false` である（3.4）。

### 6.11 画面すべてを束ねる（`buildRunView`）
- **公開する関数**: `buildRunView(outputs, viewRole)`（`src/viewer/run_view.ts`）。`buildScenarioList`・`buildScenarioDetails`・`buildIssueList`・`buildGlossaryView`・`buildMapView` を同じ入力と役割で呼び、`RunView`（`viewRole`・`scenarioList`・`scenarioDetails`・`issues`・`glossary`・`map`）にまとめる。束ねるだけで、判定や文を足さない。
- **事前条件**: 最初に `checkRunOutputs` を呼び、破れがあれば理由（`reason` とファイル）を並べた例外を投げる。画面ごとの関数も通っていない入力で例外を投げるが、どの画面の例外か分かりにくいため、入口で先に止める。起動アプリは `buildRunView` の前に `checkRunOutputs` を呼び、破れがあれば画面を作らずに `problems` を出す（1.2）。
- **リンクの表を持たない**: 1.2 では「画面どうしのリンクの表」を返すとしていたが、リンクの鍵を表示の id にしたので（6.7）、各ビューモデルが持つ表示の id でリンクを張れる。シナリオ一覧の行と詳細は `displayId`、論点は `S-01-L-001`、地図と用語辞典は `c1`・`n1` で対応する。同じ対応を別の表に写すと、2 か所の値がずれうるため、表は作らない。
- **表示の役割**: `viewRole` は起動アプリの引数をそのまま持つ。出力を書いたときの役割（`system_map.json` の `viewRole`）との関係は、6.4 の答えを待っている。
