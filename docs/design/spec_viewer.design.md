# SpecViewer 基本設計書

本設計書は、画面モジュールの仕様書（`spec_viewer.spec.md`）に規定された、1 回の実行の出力を閲覧の画面として見せる処理を、全体基本設計書（`system_solution.design.md`）の規約に準拠して**どのように技術的・構造的に実現するか（How）**を定義する。

---

## 1. アーキテクチャと全体設計制約の継承

### 1.1 全体設計制約の適用
- **2 つに分ける**: 出力のファイルから画面の中間表現（ビューモデル）を作る部分と、ビューモデルを画面に描く部分に分ける。
  - **ビューモデルを作る部分**: `specula/src/viewer/`（Pure ESM, Target: ES2022+）。ファイルの読み書きも画面の操作もしない（Zero-I/O Core）。出力のファイルの中身（パース済みの JSON と、Markdown・Mermaid の文字列）と表示の役割を受け取り、画面ごとのビューモデルを返す。`src/types/` だけを参照する。
  - **画面に描く部分**: 起動アプリ（Itera OS の app）。出力先のファイルを `FileSystemPort` で読み、ビューモデルを作る部分を呼び、結果を描く。表示の判定（役割による出し分け、未決・未検証・候補の判定）を描く側に書かない。
- **分ける理由**: 役割による出し分けと状態の判定を、テストのできる純粋な関数に閉じ込めるためである。描く側に判定を書くと、画面ごとに表示が食い違い、仕様 3.3 の「同じ項目は同じ表示」をテストで確かめられない。
- **LLM を使わない**: ビューモデルは決定論的に作る（全体設計 1.2）。
- **書き込まない**: 出力先に書き込まない（仕様 1.2）。画面の状態（開いているタブ、絞り込み）はファイルに残さない。

### 1.2 公開する関数
```typescript
buildRunView(
  outputs: RunOutputs,            // 出力先から読んだファイルの中身（2 節）
  viewRole: "PdM" | "Eng",
): RunView;                       // 4 つの画面とシナリオの詳細のビューモデル、画面どうしのリンクの表

checkRunOutputs(outputs: RunOutputs): RunOutputsCheck;   // 仕様 3.1 の事前条件
```
- `checkRunOutputs` が事前条件の破れを返したときは、起動アプリは画面を作らずに理由を表示する。
- ビューモデルの型の詳細は、画面を実装するときに決めて 6 節に書く。

## 2. 入力（出力先のファイル）

## 3. 画面ごとの項目
表の「Eng のみ」の印がある項目は、役割が `Eng` のときだけ出す。印の無い項目は、両方の役割で同じものを出す。

### 3.1 シナリオ一覧
**上部: 実行の概要**（元: `run_report.json`）

| 項目 | 元のデータ | 備考 |
| :--- | :--- | :--- |
| 解析したファイルの数・解析に失敗した数 | `system.parsedFileCount`・`parseFailureCount` | |
| Bounded Context・コマンド・イベントの数 | `system.boundedContextCount`・`commandCount`・`eventCount` | |
| シナリオの数と内訳 | `totals.completed`・`ambiguous`・`stopped` | 「仕様になった」「曖昧さで止まった」「途中で止まった」と書く |
| 曖昧さの件数 | `totals.ambiguity` | `PdM` では「エンジニアの確認待ち: N 件」と合計だけを出す。`Eng` では種類ごとに出す |
| 検証の状態の内訳 | `totals.verification` | `NONE_FOUND_WITHIN_SCOPE` は「指定の範囲で、行った検査では見つからなかった」と書く |
| 検査の範囲 | `inspectionScope` | 「検査はシナリオごとに行った。シナリオどうしの矛盾は見ていない」（`unit`）と、行っていない検査（`invariantChecks` が `NOT_APPLICABLE` なら「不変条件の検査はしていない」、`scenariosWithoutVerification` のシナリオは「検証の結果が無い」） |
| 未生成の数 | `glossary.notGenerated`・`intents.notGenerated` | 0 件でなければ目立たせる |
| 読んだ資料の数 | `glossary.documents` | 上限で読まなかった資料があれば出す |

**本体: シナリオの表**（元: `run_report.json` の `scenarios`、`intents.json`）

| 列 | 元のデータ | 備考 |
| :--- | :--- | :--- |
| 表示の id | `displayId` | 例: `S-02` |
| シナリオの名前 | 起点のコマンドまたはポリシーの、辞書の用語 | SpecProjector の仕様書の題と同じ引き方（SpecProjector 基本設計 4.1・8.4）。未生成なら「（名前は未生成）」 |
| 状態 | `kind` | 仕様になった／曖昧さで止まった／途中で止まった |
| 検証 | `outcome`・`unverifiedReason` | 仕様になったシナリオだけ。未検証なら理由を出す |
| 件数 | 論点の件数（`issueCount`）、または曖昧さの件数（`counts` の合計） | 曖昧さは `PdM` では「エンジニアの確認待ち: N 件」 |
| 意図の候補 | `intents.json` のシナリオの意図 | 1 行で切り、確定の状態の印を付ける |
| Bounded Context | `boundedContext` を用語にしたもの | Bounded Context が 1 つだけなら列を出さない |
| 起点の所在（Eng のみ） | `implementation_map.json` | |

- 絞り込み: 状態、Bounded Context、検証の状態。並び: 既定は表示の id の順。件数の多い順にも並べ替えられる。

### 3.2 シナリオの詳細
**冒頭**（すべてのタブで共通）

| 項目 | 元のデータ | 備考 |
| :--- | :--- | :--- |
| 表示の id・シナリオの名前・Bounded Context | `run_report.json`・辞書 | |
| 意図の候補 | `intents.json` | 確定の状態の印。未生成ならその理由 |
| 利用者が書いた目的 | `userIntent` | 利用者が定義したシナリオで、目的があるときだけ |
| 起点の種類 | `run_report.json` のシナリオの行の `inletType` | `COMMAND` は「操作」、`POLICY` は「反応」と書く |
| アクター・画面のルート・期待イベント | `run_report.json` のシナリオの行の `actor`・`route`・`expectedEvent` | 画面を持たないシナリオでは `route` が `null` なので、画面のルートを出さない |
| 検証の状態 | `ledger.json` の検証の状態 | 論点より前に置く |
| 検査の範囲 | 固定の文 | 「このシナリオだけを検査した。ほかのシナリオとの矛盾は見ていない」 |
| 論点の件数 | `ledger.json` | 仕様不備一覧へのリンク |

**タブ**（仕様になったシナリオだけ）

| タブ | 元のデータ | 備考 |
| :--- | :--- | :--- |
| 仕様書 | `spec.md` | |
| 操作の一覧表 | `matrix.md` | 各行の「関わる論点」から仕様不備一覧へリンクする |
| 操作の流れ図 | `flow.mmd` | |
| 形式仕様のソース（Eng のみ） | `spec.als` | 付録として扱う |

- 曖昧さで止まったシナリオは、冒頭だけを出し、タブの代わりに「このシナリオは、エンジニアの確認待ちの箇所が N 件あるため、形式仕様にできなかった」を出す。`Eng` では、仕様不備一覧（このシナリオで絞り込み）へのリンクも出す。

### 3.3 仕様不備一覧
| 種類 | 元のデータ | PdM | Eng |
| :--- | :--- | :--- | :--- |
| 論点 | シナリオごとの `ledger.json` | 出す | 出す |
| 曖昧さ | シナリオごとの `ambiguity.json` | シナリオごとの件数だけ（「エンジニアの確認待ち」） | 質問・箇所・原文をすべて出す |

**論点の項目**

| 項目 | 元のデータ | 備考 |
| :--- | :--- | :--- |
| 表示の id | `S-01-L-001` …（SpecProjector 基本設計 8.7） | 論点カタログの識別子（`LEDGER-…`）は出さない |
| シナリオ・関わる操作 | `ledger.json` | 操作の一覧表の該当する行へのリンク |
| 種類 | 未定義遷移・操作の重なり・到達できない操作・デッドロック | |
| 主張・観測事実・判断質問 | LLM の文 | 確定の状態の印。未生成ならその理由 |
| 選択肢 | 種類ごとに決まった 3 つ | どれも採択済みとして見せない |
| 決定 | 初回は常に未決 | 「未決」と分かる見た目にする |
| 実行列 | 最短の実行列 | 到達できない操作には無い |
| 従属する反例の数 | `ledger.json` | |

**曖昧さの項目**（Eng のみ）

| 項目 | 元のデータ | 備考 |
| :--- | :--- | :--- |
| 表示の id | `S-02-A-001` … | |
| シナリオ | 表示の id と名前 | シナリオの詳細へのリンク |
| 種類 | `kind` | 値が決まらない／外部への作用がある／同じ条件で別の経路に進む |
| 質問 | `question.text` | 確定の状態の印。未生成ならその理由 |
| 実装の箇所と原文 | `location`・`detail` | |

- `PdM` の画面: 論点の一覧と、その下に「エンジニアの確認待ち」のシナリオ別の件数の表を置く。
- 絞り込み: 種類、シナリオ、論点の種類、曖昧さの種類（Eng）。既定ではシナリオごとにまとめ、見出しに件数を出す。

### 3.4 全体地図
- **地図 1**: Bounded Context の箱と、またぐポリシーの矢印。箱を選ぶと、用語・意図の候補（確定の状態の印）・属するシナリオの数をポップアップで出し、地図 2 と、その Bounded Context で絞り込んだシナリオ一覧へのリンクを置く。Bounded Context が 1 つだけのときは、全体地図を開いたら地図 2 を出す。
- **地図 2**: 既定はコマンド・ドメインイベント・ポリシーとそのつながり。切り替えで、アクター・リードモデル・アグリゲートを足す。切り替えは SpecProjector に地図 2 を作り直させるのではなく、SpecProjector が出した地図 2 の JSON（足す要素を含む版）の表示を切り替える。
- 要素は用語と表示の id（`c1`・`n1`）で表す。用語が未生成の要素は「〈種類〉 〈番号〉（名前は未生成）」（SpecProjector 基本設計 8.2）。
- 要素を選んだときのポップアップ: 用語、確定の状態、意味（資料の抜粋）、その要素を起点にしたシナリオ。1 つのコマンドがイベントを複数発生させるとシナリオはイベントごとに分かれるので（ScenarioExtractor 仕様 2.2）、シナリオが複数あるときは一覧から選ぶ。
- 壊れた箇所の印: 地図の JSON の印の欄が空でなければ、要素とつながりに印を描く。初回は欄が常に空である。
- 実装の名前と所在（Eng のみ）。

### 3.5 用語辞典
**用語の一覧**（元: `glossary.json`）

| 列 | 元のデータ | 備考 |
| :--- | :--- | :--- |
| 表示の id | 俯瞰図と同じ番号（`c1`…、`n1`…） | |
| 用語 | 項目の用語 | 未生成ならその理由 |
| 確定の状態 | 用語の確定の状態 | 初回はすべて「候補」か「未生成」 |
| 種類 | Bounded Context・コマンド・ドメインイベント・ポリシー | 利用者に見せるのは地図の要素だけ（GlossaryBuilder 仕様 1.2） |
| 意味 | 資料の抜粋 | 「候補」の扱い。抜粋が無ければ「資料に記述が無い」 |
| 用語の出どころ | 資料のパスと見出し | |
| またいでいる印 | 項目のまたいでいる先 | またぐポリシーは両方の Bounded Context に出す |
| 実装の名前と所在（Eng のみ） | 項目の実装の名前と所在 | |

- Bounded Context ごとに区切る。Bounded Context が 1 つだけなら区切りを出さない。

**資料とコードのずれ**（別のタブ）

| 区分 | 既定の見せ方 |
| :--- | :--- |
| 資料に記述が無い要素 | 一覧で出す |
| 同義と多義の候補（同じ Bounded Context の中） | 一覧で出す |
| Bounded Context ごとに意味が違う言葉 | 一覧で出す。ずれではなく別の区分として見せる |
| 項目に対応しない資料の名前 | 件数だけを出し、開くと一覧が見える形にする（件数が多くなりやすいため） |

## 4. 画面どうしのリンク
| リンク元 | リンク先 | 鍵 |
| :--- | :--- | :--- |
| シナリオ一覧の行（仕様になったもの） | シナリオの詳細 | シナリオ |
| シナリオ一覧の行（曖昧さで止まったもの） | `PdM`: シナリオの詳細。`Eng`: 仕様不備一覧（そのシナリオで絞り込み） | シナリオ |
| 地図 1 の Bounded Context | 地図 2、シナリオ一覧（その Bounded Context で絞り込み） | Bounded Context |
| 地図 2 のコマンド・ポリシー | シナリオの詳細（複数なら選ぶ一覧を挟む） | 地図の要素 → シナリオ |
| シナリオの詳細の論点の件数 | 仕様不備一覧（そのシナリオの論点で絞り込み） | シナリオ |
| 操作の一覧表の「関わる論点」 | 仕様不備一覧の該当する論点 | 論点 |
| 仕様不備一覧の論点 | シナリオの詳細の操作の一覧表の該当する行 | 論点 → 操作 |
| 仕様不備一覧の項目 | シナリオの詳細 | シナリオ |
| 地図・詳細・不備一覧の中の用語 | 用語辞典のポップアップ | 用語 |
| 用語辞典の項目 | 地図 2 の該当する要素 | 地図の要素 |

- 鍵は内部の識別子とする。表示の id と内部の識別子の対応は `implementation_map.json` で引く（SpecProjector 基本設計 8.5）。リンクは 1 回の実行の中で閉じる（仕様 2.3）。
- 内部の識別子は URL やアドレスバーにも出さない（`PdM` で実装の所在が見えてしまうため）。画面の中の位置を外に示すときは表示の id を使う。

| 状態 | 見た目 |
| :--- | :--- |
| 未生成 | 理由を出す |
| 候補 | 「候補」の印 |
| 確定 | 印を外す、または「確定」の印 |

## 6. 実装のときに決めたこと
2026-10-31 に決めた。画面ごとのビューモデルの型は、その画面を実装するときにこの節へ足す。

### 6.1 出力先の読み方（`RunOutputs`）
- 読むのは `src/lib/read_outputs.ts` の `readRunOutputs(fs: FileSystemPort, outDir: string): Promise<RunOutputs>` とする。ファイルを読むので `src/viewer/` には置かず、書く側の `src/lib/write_outputs.ts` と対にする。
- 読むファイルは 2 節の表のものだけである。`system_map.mmd`、シナリオごとの `spec.json`・`solver_report.json`・`ambiguity.md` は画面で使わないので読まない。
- シナリオのディレクトリは、`run_report.json` の `scenarios` から `scenarios/<safeName(scenarioId)>/` として引く。`FileSystemPort.list` は順序を保証しないので、ディレクトリの一覧からは引かない。読むファイルはシナリオの `kind` で決める（`COMPLETED`: `spec.md`・`matrix.md`・`flow.mmd`・`spec.als`・`ledger.json`、`AMBIGUOUS`: `ambiguity.json`、`STOPPED`: なし）。`run_report.json` が無いか読めないときは、シナリオのファイルを読まない。
- ファイルごとの結果は、次の 3 通りのどれかで持つ。読めなかったことを `null` 1 つにまとめないのは、無いのか壊れているのかで表示する理由が違うためである。
  - `{ kind: "OK", value }`: JSON はパースした値、Markdown・Mermaid・Alloy は文字列。
  - `{ kind: "MISSING" }`: ファイルが無い。
  - `{ kind: "INVALID", reason }`: JSON としてパースできない。
- `readRunOutputs` は形の検査をしない（JSON のパースだけ）。形と組み合わせの検査は `checkRunOutputs` で行う。

### 6.2 事前条件の検査（`checkRunOutputs`）
- 返すのは `{ ok: boolean; problems: RunOutputsProblem[] }` とする。`ok` が `false` のとき、起動アプリは画面を作らずに `problems` を表示する（1.2）。
- 画面を作れないもの（`ok` を `false` にするもの）:
  - `run_report.json` が無いか、読めない。
  - 読めた JSON のファイルが壊れている（`INVALID`）。
  - `basis` を持たない（`basis` を足す前の古い出力）。
  - `run_report.json`・`glossary.json`・`intents.json`・`implementation_map.json`・`system_map.json` のうち、あるものどうしの `basis`（`mapHash`・`documentsHash`）が一致しない（仕様 3.1）。
  - `run_report.json` のシナリオの `kind` から決まるシナリオのファイルが無い（同じ実行の書き出しなら必ずあるため）。
- 画面を作れるもの（`problems` に入れない）: 仕様 2.1 で任意とされている `glossary.json`・`intents.json`・`implementation_map.json`・`system_map.json` が無いこと。どの画面で何を出すかは `buildRunView` が決める（例: 辞書が無ければ要素の名前を「辞書が無い」と表示する。全体地図は俯瞰図が無ければ理由を出す）。
- 表示の役割と `system_map.json` の `viewRole` の関係は、6.4 が決まるまで検査しない。

### 6.3 ビューモデルの型の方針
- 型は `src/viewer/types.ts` に置き、`src/types/` だけを参照する。
- 本文の文と確定の状態は組で持ち、描く側は印を付けるだけにする（5 節）。描く側で状態を判定しない（1.1）。
- 画面どうしのリンクの鍵（内部の識別子）は、ビューモデルの中のリンクの表だけに置き、描く文字列には入れない（4 節）。

### 6.4 画面の描き方
- **依存を足さない**: Itera OS が配布する外部ライブラリ（`MetaOS.vendor`）は MathJax・Monaco・pdf.js・pdf-lib で、Mermaid と Markdown の描画のライブラリは無い。そのため、出力を描く処理を自分で書く。範囲は SpecProjector が出すものに限る。
  - **Markdown**（`spec.md`・`matrix.md`）: SpecProjector が出す記法（`render_document.ts`・`render_matrix.ts` の見出し・段落・箇条書き・番号付きの箇条書き・表・引用・コードブロック）だけを、ブロックの木に分ける純粋な関数を `src/viewer/` に置く。
    - 行の中の書式（強調・インラインのコードなど）は解釈せず、文字のまま出す。SpecProjector は行の中の書式を出さず、LLM の文は改行を空白にするだけで Markdown の記号を逃がしていない（`escape.ts` の `mdLine`）ため、解釈すると LLM の文の記号が書式に化ける。
    - 表のセルの `\|` は `|` に戻す（`mdCell`）。コードブロックの囲みは 3 つ以上のバッククォートで、長さはソースによって変わる（`fenceFor`）。
  - **地図と流れ図**: 地図は `system_map.json` から、流れ図は `flow.mmd`（SpecProjector の流れ図が出す範囲の flowchart）から、ノードとつながりのグラフを作り、層に並べる純粋な配置の関数を `src/viewer/` に置く。描く側は配置の結果を SVG にするだけにする。
- **LLM の文は `textContent` で描く**: 用語・意図・論点の文・質問の文は LLM が作り、LLM は解析対象のコードと資料を読んでいる。そのため、`innerHTML` に入れず、文字列として描く。
- **表示の役割の切り替え**: 今の出力は、利用者向けのビュー（仕様書・操作の一覧表・流れ図・曖昧さの一覧・俯瞰図）を 1 つの役割で書く。仕様 1.1 の「Global Menu で役割を切り替える」を満たすには、出力の役割に固定するか、両方の役割のビューを書き出すかを決める必要がある。中瀬古様の答えを待っている（2026-10-31）。
