# FormalSolver 基本設計書

本設計書は、形式仕様検証モジュールの仕様書（`03_formal_solver.spec.md`）に規定された全状態空間探索および分割統治による自律検証を、全体基本設計書（`system_solution.design.md`）の規約に準拠して**どのように技術的・構造的に実現するか（How）**を定義する。

---

## 1. アーキテクチャと全体設計制約の継承

### 1.1 全体設計制約の適用
- **配置場所**: `specula/src/core/formal_solver.js`（Pure ESM, Target: ES2022+）。
- **Zero-I/O Core の遵守**: コアに置くのは「検査コマンドの組み立て」と「エンジンの出力の読み取り・正規化」だけとする。検証エンジンの実行は外部プロセスで行い、コアは抽象インターフェース `SolverPort` を介してのみ呼び出す（`FileSystemPort` と同じ依存性逆転）。
- **依存方向の一方向性**: コアは `src/ports/` の型定義のみを参照し、エンジンの所在（ローカルマシン、CI）を知らない。

### 1.2 ソルバアーキテクチャ (Single Engine via SolverPort)
「LLM単体に論理計算をさせない」原則と移植性の要求に基づき、**検証エンジンは Alloy 6 の 1 系統に限る**。
実行環境ごとにエンジンを使い分けると、同じ仕様でも環境によって結果が変わり、移植性に反するためである。

```
[FormalSpec (*.als)] ──➔ [Check Command Builder] ──➔ [Complexity Estimator]
                                                              │
                                                              ▼
                                                   [Compositional Slicer]
                                                    (状態爆発時の自律分割統治)
                                                              │
                                                              ▼
                                                        «SolverPort»
                                     ┌────────────────────────┴────────────────────────┐
                                     ▼                                                 ▼
                     [LocalBridgeAlloyAdapter]                               [CliAlloyAdapter]
                  (Itera OS からローカルブリッジ経由で              (CI / Node.js から java を
                   手元のマシンの Alloy 6 を起動)                      直接起動)
                                     └────────────────────────┬────────────────────────┘
                                                              ▼
                                                [Report Normalizer]
                                                              │
                                                              ▼
                                            [SolverReport (元の記録・決定論的出力)]
```

- **`SolverPort`**: 入力は Alloy のソースと検査コマンドの一覧、実行条件（スコープ、SAT ソルバ）。出力はエンジンの生の結果と、実際に使われた Alloy の版・SAT ソルバの版。
- **アダプター**:
  - `LocalBridgeAlloyAdapter`: Itera OS（ブラウザ）から、ローカルブリッジ経由で手元のマシンの Alloy 6 を起動する。ブラウザ内では Java 製の Alloy を直接動かせないため、この経路をとる。
  - `CliAlloyAdapter`: Node.js / CI から `java` で Alloy 6 を直接起動する。
- **エンジンに到達できないとき**: 検証を行わず、到達できなかったことを `SolverReport` に記録して返す。簡易なエンジンで代わりに判定することはしない。
- **将来の選択肢（現時点では作らない）**: Alloy から SAT への変換部を自前で持ち、同じ SAT ソルバ（WebAssembly 版など）をどの環境でも使う構成。処理能力の低いマシンで WebAssembly の実行が難しい場合があるため、まずは外部実行とする。

## 2. 検査項目と Alloy 6 での実現 (Detailed Algorithms)

以下の検査は、すべて Alloy 6 の検査コマンド（`check` / `run`）として組み立て、エンジンに解かせる。コア側で状態空間を自前探索することはしない。

### 2.1 未定義遷移の検査 (State × Command)
- 状態集合 $S$ と操作述語集合 $C$ の各組 $\langle s \in S, c \in C \rangle$ について、「状態 $s$ で操作 $c$ の事前条件が満たされるが、遷移先が定まらない」インスタンスが存在するかを検査コマンドとして生成する。
- インスタンスが見つかった組を「未定義遷移（Unhandled Transition）」として記録する。

### 2.2 デッドロックおよび到達不能性の検査
- 初期状態 $s_0$ から到達できない状態が存在するかを検査する。
- 終端状態（Terminal）として明示的にタグ付けされていないにもかかわらず、どの操作でも脱出できない状態が存在するかを検査し、「デッドロック（復帰不能）」として記録する。

### 2.3 最小反例トレースの導出
- 安全プロパティ（`assert`）ごとに、時相ステップ数の上限を 1 から順に増やして検査し、**最初に反例が見つかった長さを最短**とする。
- 同じ長さの反例が複数ありうる場合でも、どのトレースが返るかは SAT ソルバとその版に依存しうる。このため、実行条件（2.4）を記録し、決定論性は「同一の実行条件のもとで」約束する。

### 2.4 実行条件の記録 (Reproducibility)
- `SolverReport` に次を必ず記録する: Alloy の版、SAT ソルバの名前と版、スコープ（インスタンス数・時相ステップ数）、分割の有無と分割単位、境界で確かめた不変条件。
- `SolverReport` は**元の記録**であり、反例を要約・省略しない。要約は `LedgerSynthesizer` が行う。

## 3. 分割統治による自律的自己解決 (Compositional Slicing)

全探索時の状態爆発を人間を介さずに自律解決するアルゴリズム：
1. **計算量見積もり**: 状態数と探索スコープから探索空間サイズを試算。閾値を超える場合、一括探索を停止。
2. **シナリオ単位のスライシング**:
   - 仕様全体を、独立したサブグラフ（シナリオ単位 / 境界づけられたコンテキスト単位）に自動分割。
3. **境界不変条件を用いた合成的検証**:
   - 各サブグラフを検証し、コンテキスト間の越境イベントに対しては「大域不変条件」が破られないかをインターフェースレベルで検証。
   - すべてのサブグラフ検証を結合し、単一の統合 `SolverReport` として出力する。
4. **検査範囲の明記**:
   - 分割した場合、境界の不変条件として表明されていない越境性質は検査されない。この事実と、確かめた境界不変条件の一覧を `SolverReport` に明記する。
