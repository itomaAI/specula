# 汎用仕様抽出・検証システム 全体基本設計書 (System Solution Design)

本設計書は、システム全体仕様書（`system_solution.spec.md`）に規定された振る舞い・契約を**どのように技術的・構造的に実現するか（How）**を定義する。

## 1. 根本思想: 3アクター分担と Loom オーケストレーション

### 1.1 3 アクターの責任分界点 (Division of Labor)
本システムの中核思想は、**「LLM単体に論理的計算・証明をさせない」**ことである。
LLMを「計算機」ではなく、**「人間と数学的決定論的ソルバ（計算機）の間を取り持つ翻訳・合成インターフェース」**として位置づける。

| アクター | 役割の定義 | 担当する具体的な処理 | 禁忌（アンチパターン） |
| :--- | :--- | :--- | :--- |
| **人間 (PdM / 意思決定者)** | **「意図」と「価値判断」** | 要求の提示、意思決定論点（Domain Ledger）に対する判断・コミット | 全状態探索、エッジケースの網羅的暗算 |
| **LLM (Orchestrator / Agent)** | **「翻訳」と「文脈の畳み込み」** | コードから事実の抽象化、反例の自然言語逆翻訳、コンテキストの要約 | 仕様の矛盾の「推測解決」、論理証明の自己完結 |
| **外部ソルバ (Solver)** | **「決定論的証明」と「全状態探索」** | $N \times M$ の全状態空間探索による矛盾・未定義・デッドロックの検出 | 自然言語の解釈、ビジネス要件の勝手な補完 |

## 3. Loom ライフサイクルの全体実装

本システム全体のオーケストレーションは、Loom の 3 大操作をパイプライン全体に渡って適用することで駆動される：

### 3.1 「置く（分解 / Decompose）」のフロー
1. **マクロ置く**: M0 がリポジトリ全体から Bounded Context（プロジェクト）を同定し、Event Storming 全体マップ上に境界を敷く。
2. **ミクロ置く**: M0 がコマンド・ポリシーを起点として個別シナリオ（タスク）をアトミックに切り出す。
3. **事実スライス置く**: M1 が各個別シナリオの因果境界（Inlet ➔ Outlet）のみをピンポイントで切り出し、M2 が形式仕様述語へとコンパイルする。

### 3.2 「畳む（集約 / Fold）」のフロー
1. **論点の集約**: M3 が検出した反例を M4 が因果依存関係に基づいて「根本論点」へと集約（トポロジカルソート）する。
2. **親文脈への還元**: 人間が合意した意思決定結果（Domain Ledger）および証明完了事実を、親である Bounded Context の「仕様正本・ドメイン文脈」へと折りたたむ。

### 3.3 「移す（伝播 / Transfer）」のフロー
1. ある Bounded Context（例: `ユーザー認証`）のシナリオ完了で確定したドメインイベント（例: `UserRegistered`）を、別コンテキスト（例: `通知基盤`）のポリシー起動トリガーへと越境伝播させる。
2. 両コンテキストは直接結合せず、Event Storming Map 上の共有イベント定義のみを介して疎結合に結合する。

## 4. アーキテクチャ特性と物理構造規約

### 4.1 Zero-I/O Core と環境ポータビリティ
本システムはブラウザ（Itera OS / Web Worker）、CLI（Node.js）、および CI/CD（GitHub Actions）の全環境で同一コードベースで動作する。
- **Core モジュールの純粋性**:
  - `M0` 〜 `M5` の全コアモジュールは、直接 `fs` や `fetch`、DOM を一切インポートしない。
  - すべてインメモリデータを受け取り、インメモリデータを返す純粋計算関数として設計する。
- **依存性逆転 (Ports & Adapters)**:
  - 外部環境との入出力は抽象インターフェース `FileSystemPort` を経由し、実行時にアダプターを注入する。

### 4.2 リポジトリ構造規約
