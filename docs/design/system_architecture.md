# 汎用仕様抽出・検証システム 全体アーキテクチャ設計書

本設計書は、形式仕様言語を唯一の正本（Single Source of Truth）とし、ソースコード（画面の情報があるときはそれも）からの仕様抽出、ソルバによる上限つきの網羅的な検査（スコープとステップ数の範囲で行う）、LLMによる論点逆翻訳、および同じ正本からの複数のビューへの射影を実現するシステムの**全体アーキテクチャ規約、責任分界点、システムデータフロー、大域的不変条件、および実行基盤方針**を定義する。

---

## 1. 全体アーキテクチャ規約 (Architectural Principles)

本システムは、プロダクトマネージャー（PdM）が形式仕様を直接記述・検証・履歴管理できるプラットフォームの中核エンジンである。以下の根本思想をシステム全体の最高規約として位置づける。

### 1.1 根本思想: LLM単体に論理的思考（計算・証明）をさせない
LLMは本質的に確率的（Probabilistic）なテキスト生成器であり、決定論的な網羅性の担保や矛盾の証明を原理的に行うことができない。そのため、LLMを「計算機」としてではなく、**「人間と決定論的ソルバ（計算機）の間を取り持つ翻訳インターフェース」**として配置する。事実の抽出と検証は決定論的な外部ツールに任せ、LLM は要約と翻訳だけを行う。

### 1.2 Loom 双対構造（プロジェクト／タスク）の大域的適用
システム全体の知識と実行単位は、Loom の基本構造に完全に一致させる：
- **プロジェクト相当 (Bounded Context / System Root)**:
  - 終わらない意図（Why）と文脈（Event Storming 全体マップ）を保持する大域的な器。
- **タスク相当 (Individual Command)**:
  - 単一の明確な完了条件を持つ、アトミックな1回の因果スライス（Command/Policy ➔ Expected Event）。

### 1.3 形式仕様言語の正本化 (Single Source of Truth)
人間が直接編集するUIやMarkdown、および機械が検証するテストコードはすべて二次的な「射影（Projection）」にすぎない。リポジトリに永続化される唯一の正本は、数学的関係論理を備えた形式仕様言語コード（Formal Specification Code）とする。

## 2. 3 アクターの責任分界点 (Division of Labor)

システムを構成する 3 つのアクター（人間、LLM、外部ツール）の役割と責務を厳格に分離し、相互のアンチパターンを排除する。

| アクター | 役割の定義 | 担当する具体的な処理 | 扱わないこと（アンチパターン） |
| :--- | :--- | :--- | :--- |
| **人間 (PdM / 意思決定者)** | **「意図」と「価値」の定義** | 要求・シナリオの記述、意図の確定、意思決定論点（Domain Ledger）に対する判断 | エッジケースの網羅的洗い出し、状態遷移の数式化 |
| **LLM** | **「翻訳」と「要約」** | 抽出済みの事実への命名、実装の語からドメインの語への言い換え、反例の自然言語化、意図の候補の文 | コードからの事実の抽出、仕様の矛盾の「推測」、自律的な論理の証明、選択肢の採択 |
| **外部ツール（パーサとソルバ）** | **「決定論的な抽出」と「上限つきの網羅的な検査」** | `@babel/parser` による AST の構築、Alloy 6 による形式仕様コードの検査（スコープとステップ数の範囲での、未定義遷移・操作の重なり・到達できない操作・デッドロックの検出） | 自然言語の解釈、ビジネス要件の妥当性の判断 |

処理ごとの LLM の担当と決定論性の約束は、`system_solution.design.md` の 1.2 に一覧する。

## 3. システムデータフローと Loom ライフサイクル (Data Flow & Workflows)

システムは独立したモジュール（CommandExtractor・GlossaryBuilder・IntentSynthesizer・ContextExtractor・FormalTranspiler・FormalSolver・LedgerSynthesizer・SpecProjector）で構成され、Loom の 3 つの基本操作によって統制される。パイプラインが出力先に書いたファイルは、画面モジュール（SpecViewer。`spec_viewer.spec.md`）が読んで閲覧の画面にする。SpecViewer はパイプラインの段ではなく、出力を読むだけで書き込まない。モジュールは番号を持たず、それぞれ独立した道具として呼び出せる。下の図の順は、パイプラインがモジュールを呼ぶ順である。初回の実行で行うのは「置く」と、検証・論点の整理・射影までである。人間の合意を受けて行う「畳む」と「移す」は 2 回目以降の実行で行う（全体仕様 1.5）。現在の設計と実装の範囲は初回の実行である。

### 3.1 パイプラインの構成

```
【フェーズ A: 初回の実行（現在の範囲）】
  [リポジトリ全体 (コード/Docs/画面)]
                 │
                 ▼ (CommandExtractor)     【置く: プロジェクト / タスク】
  [EventStormingMap (全体マップ。名前と意図を持たない)] ＆ [CommandTarget[] (個別シナリオ群)]
                 │
                 ▼ (GlossaryBuilder)       【のぞく: 用語・実装名との対応・資料とのずれ】
  [Glossary (ユビキタス言語辞書)]
                 │
                 ▼ (IntentSynthesizer)     【候補: 意図】
  [IntentCatalog (Bounded Context とシナリオの意図の候補)]
                 │
                 ▼ (ContextExtractor)     【抽出: 厳密因果スライス。ここからシナリオごと】
  [RawContextModel (シナリオ垂直事実モデル)]
                 │
                 ▼ (FormalTranspiler)     【昇華: 形式モデル変換】
  ┌────────────────────────────────────────────────────────┐
  │ ★【唯一の永続化正本】 形式仕様コード (`FormalSpec`)   │
  │   （状態を決められないシナリオは AmbiguityReport で止まる）│
  └──────────────┬───────────────────┬─────────────────────┘
                 │ (FormalSolver)    │ (SpecProjector)
                 ▼ 【上限つきの検査】▼ 【射影】
  [SolverReport (反例トレース        [SpecificationView]
   または未検証と理由)]               ・仕様書 (Markdown)
                 │                   ・操作の一覧表 / 操作の流れ図 (Mermaid)
                 ▼ (LedgerSynthesizer)     ・全体の俯瞰図（全体マップと辞書から）
                 │                   ・曖昧さの一覧 / 実装との対応表（辞書から）
  [DomainLedgerCatalog (意思決定論点。初回はすべて未決)]
                 │
                 ▼
【フェーズ B: 2 回目以降の実行（現在の範囲外）】
  [人間 (PdM) による判断] ➔ 【畳む】[親コンテキストの文脈へ還元]
                          ➔ 【移す】[別コンテキストのポリシーへ伝播]
```

### 3.2 Loom 3大操作によるライフサイクル統制

1. **置く（分解 / Decompose）**（初回から行う）:
   - `CommandExtractor` がシステム全体から Bounded Context（プロジェクト）を同定し、個別シナリオ（タスク）をアトミックに切り出す。
   - `ContextExtractor` が各個別シナリオの境界（Inlet ➔ Outlet）のみをピンポイントで抽出し、`FormalTranspiler` が形式仕様コードへコンパイルする。
   - `FormalSolver` が反例を探索し、`LedgerSynthesizer` が反例を論点に整理する。この整理は反例を論点にまとめる処理であり、「畳む」には当たらない。
2. **畳む（集約 / Fold）**（2 回目以降）:
   - 人間が合意した意思決定結果（Domain Ledger の決定）を、親コンテキストの「文脈（全体イベントストリーム・仕様正本）」へと畳む。
3. **移す（伝播 / Transfer）**（2 回目以降）:
   - あるコンテキストのシナリオ完了で確定したドメインイベントを、別コンテキストのポリシー起動トリガーへと越境伝播させる。
   - コンテキスト間は直接コード参照を持たず、Event Storming Map 上の共有イベント定義のみを介して疎結合に結合する。

## 4. 大域的不変条件と契約仕様 (Global Invariants & Contracts)

### 4.1 大域的事前条件 (Global Preconditions)
1. **原本の非破壊性**: 入力されるソースコードおよび画面画像は Read-only として参照され、システムはこれを直接改変しない。
2. **正本の単一性**: 仕様の正本は形式仕様言語で記述されたコードただ 1 系統のみであり、他のすべてのドキュメント（Markdown/図）はそこからのオンデマンド射影であること。

### 4.2 大域的事後条件 (Global Postconditions)
1. **数学的健全性 (Soundness)**: ソルバによって**指定スコープ内で**検出されたすべての不変条件違反・未定義遷移は、漏れなく元の記録（`SolverReport`）に残り、そこからたどれる形で人間に提示されること。
   - `SolverReport` は**元の記録**であり、全件と実行条件（Alloy の版、SAT ソルバ、スコープ、時相のステップ数、分割の有無。現在は分割しない）を保持する。「漏れなく」の約束はここに課す。
   - ソルバに届かなかったときの `SolverReport` は「未検証」とその理由だけを持つ。未検証の報告を、反例が無かった報告として扱わない。
   - `DomainLedgerCatalog` は**要約（コピー）**であり、根本論点を優先してまとめてよい。その代わり、どの `SolverReport` の反例 N 件を論点 k 件にまとめたか、および従属として後ろに回した反例がどれかを必ず記録する（Loom で文脈を畳むときに「… まで／N 件」を書くのと同じ流儀）。
   - 形式仕様正本が更新されると、それより前の `SolverReport` から作った `DomainLedgerCatalog` は古くなる。古いことが分かる印を付け、再検証を促す。
2. **完全隠蔽性（利用者向けの表示）**: 利用者向けの表示（仕様書、図式、論点カタログ、曖昧性の一覧）と、形式仕様正本の公開識別子には、実装のファイルのパス、関数や変数の名前、行番号、コードの断片を出さないこと。
   - 実装との対応は捨てずに、ユビキタス言語辞書（`Glossary`）に持つ。辞書には、用語と、用語と実装名の対応を載せる。**実装との対応表**（`implementation_map.json`）は、表示に出す識別子（表示の id）からファイル・関数・行を引くために、辞書と実行の結果から作る射影である（`system_solution.design.md` の 2.2）。
   - 辞書と対応表は仕様の正本ではない（4.1 の 2）。正本は形式仕様のコードだけである。
   - 表示には役割がある。`PdM`（既定）は実装の名前を出さない。`Eng` は、対応表を引いて実装の名前を併記する。どちらの役割でも、本文の文（表示名、意図、質問、論点の文）は同じものを使い、`Eng` は対応の欄を足すだけにする。
   - 原本との対応を示す出どころ注釈（`@source` など）は正本の中に保持してよい。`PdM` の表示では必ず取り除く。
   - 2026-10-30 に改めた（中瀬古様の依頼 C0AF4DJJK8A 1793350361.074149「完全に外すのではなくマッピングを裏側で持って別表示可能に」）。それまでは、射影と論点カタログから対応を取り除くだけで、引き直す手段が無かった。

### 4.3 大域的不変条件 (Global Invariants)
1. **完全決定論性の不変条件 (Determinism Invariant)**:
   同一の形式仕様正本からは、1秒後でも1年後でも、出力される仕様書 Markdown および図式テキストはバイト単位で 100% 完全一致しなければならない。
   - これは決定論的な処理（射影など）に対する約束である。LLM を使う処理は、出力を記録して再利用することで一致させる。担当の一覧は `system_solution.design.md` の 1.2 にある。
2. **決定事項の不破壊性 (Preservation of Accepted Invariants)**:
   人間が一度承認・コミットしたドメイン不変条件（Domain Ledger における合意結果）は、下流のコード変更や再生成によって自動上書き・削除されてはならない。
   - 初回の実行では、合意結果はまだ無い。論点はすべて未決として出力し、LLM や機械が選択肢のどれかを採択した扱いにしない。

## 5. 実行基盤およびインフラ方針 (Runtime & Infrastructure Policy)

1. **言語・ビルド方針**:
   - **開発言語**: **TypeScript (`.ts`)**。厳格な静的型チェックと契約インターフェースを保持。
   - **ビルド・実行**: `tsc` でターゲット **ES2022 の純粋な JavaScript (`.js`, Pure ESM)** へコンパイルして `dist/` へ出力する。Itera OS 用には `esbuild` で 1 ファイルにまとめる。`dist/` はリポジトリに置かない。ビルド・テスト・CI・依存の方針の詳細は `system_solution.design.md` の 4.2 にある。
   - Node.js（コマンドラインと CI）と Itera OS（ブラウザ）の両方で、同じコアのコードがほかのサービスに頼らず単独で動く。環境の差はアダプターに閉じ込める（`system_solution.design.md` の 4.1）。
2. **ソルバエンジン**:
   - **検証エンジンは Alloy 6 の 1 系統に限る**。実行環境ごとに別のエンジンを使い分けない（同じ仕様の検証結果が環境によって変わると、移植性に反するため）。
   - エンジンは外部プロセスとして実行し、コアは `SolverPort` を介して呼び出す。アダプターは、Itera OS からローカルブリッジ経由で手元のマシンの Alloy 6 を起動するもの（`LocalBridgeAlloyAdapter`）と、CI / Node.js から `java` で直接起動するもの（`CliAlloyAdapter`）の 2 つとする。
   - Alloy から SAT への変換部を自前で持ち、WebAssembly 版などの同じ SAT ソルバをどの環境でも使う構成は、将来の選択肢として残す（処理能力の低いマシンで WebAssembly の実行が難しい場合があるため、現時点では作らない）。
3. **LLM**:
   - コアは `LanguageModelPort` を介して LLM を呼ぶ。アダプターは、Itera OS 版で使うもの（`IteraLlmAdapter`）と、Standalone 版で Claude Code CLI を起動するもの（`ClaudeCodeCliAdapter`）の 2 つとする。
   - Itera OS 版は利用者それぞれの Itera OS に app として配り、LLM を直接呼ばない。`IteraLlmAdapter` は、LLM の依頼をその Itera OS の AI エージェントに内部のタスクとして渡し、答えをファイルで受け取る（`system_solution.design.md` の 4.1）。
   - LLM に届かないときは、その項目を「未生成」として出力し、機械的に作った文や名前で埋めない。
4. **データ永続化**:
   - 形式仕様言語コードを唯一の仕様正本として永続化する。
   - LLM の出力の記録（`llm-records/`）も、決定論性の約束のために出力先に保存する。これは仕様の正本ではなく、再実行で同じ文を使うための記録である。
   - 辞書（`glossary.json`）・意図の候補（`intents.json`）・実装との対応表（`implementation_map.json`）も出力先に保存する。どれも正本ではなく、正本と全体マップを読むための記録である。
