# 汎用仕様抽出・検証システム 全体アーキテクチャ設計書

本設計書は、形式仕様言語を唯一の正本（Single Source of Truth）とし、ソースコードおよび視覚情報（画面画像）からの仕様抽出、ソルバによる全状態空間数学検証、LLMによる論点逆翻訳、および多面的決定論的射影を実現するシステムの**全体アーキテクチャ規約、責任分界点、システムデータフロー、大域的不変条件、および実行基盤方針**を定義する。

---

## 1. 全体アーキテクチャ規約 (Architectural Principles)

本システムは、プロダクトマネージャー（PdM）が形式仕様を直接記述・検証・履歴管理できるプラットフォームの中核エンジンである。以下の根本思想をシステム全体の最高規約として位置づける。

### 1.1 根本思想: LLM単体に論理的思考（計算・証明）をさせない
LLMは本質的に確率的（Probabilistic）なテキスト生成器であり、決定論的な網羅性の担保や矛盾の証明を原理的に行うことができない。そのため、LLMを「計算機」としてではなく、**「人間と決定論的ソルバ（計算機）の間を取り持つ翻訳インターフェース（Agent）」**として配置する。

### 1.2 Loom 双対構造（プロジェクト／タスク）の大域的適用
システム全体の知識と実行単位は、Loom の基本構造に完全に一致させる：
- **プロジェクト相当 (Bounded Context / System Root)**:
  - 終わらない意図（Why）と文脈（Event Storming 全体マップ）を保持する大域的な器。
- **タスク相当 (Individual Scenario)**:
  - 単一の明確な完了条件を持つ、アトミックな1回の因果スライス（Command/Policy ➔ Expected Event）。

### 1.3 形式仕様言語の正本化 (Single Source of Truth)
人間が直接編集するUIやMarkdown、および機械が検証するテストコードはすべて二次的な「射影（Projection）」にすぎない。リポジトリに永続化される唯一の正本は、数学的関係論理を備えた形式仕様言語コード（Formal Specification Code）とする。

---

## 2. 3 アクターの責任分界点 (Division of Labor)

システムを構成する 3 つのアクター（人間、LLM、外部ソルバ）の役割と責務を厳格に分離し、相互のアンチパターンを排除する。

| アクター | 役割の定義 | 担当する具体的な処理 | 扱わないこと（アンチパターン） |
| :--- | :--- | :--- | :--- |
| **人間 (PdM / 意思決定者)** | **「意図」と「価値」の定義** | 要求・シナリオの記述、意思決定論点（Domain Ledger）に対する判断・コミット | エッジケースの網羅的洗い出し、状態遷移の数式化 |
| **LLM (Agent / Orchestrator)** | **「翻訳」と「文脈の畳み込み」** | コードから事実の抽象化、反例の自然言語逆翻訳、コンテキストの要約 | 仕様の矛盾の「推測」、自律的な論理の証明、数学的完全性の自己担保 |
| **外部ソルバ (Solver)** | **「決定論的な証明」と「全状態探索」** | 形式仕様コードのコンパイル、$N \times M$ の全状態空間探索による矛盾、デッドロック、状態の到達不能性の検出 | 自然言語の解釈、ビジネス要件の妥当性の判断 |

## 3. システムデータフローと Loom ライフサイクル (Data Flow & Workflows)

システムは 6 つの独立モジュール（M0〜M5）で構成され、Loom の 3 大操作によって統制される。

### 3.1 6 モジュールパイプライン構成

```
【フェーズ A: 能動的初期抽出 (Bootstrap / Reverse)】
  [リポジトリ全体 (コード/Docs/画面)]
                 │
                 ▼ (M0: ScenarioExtractor) 【置く: プロジェクト / タスク】
  [EventStormingMap (全体マップ)] ＆ [ScenarioTarget[] (個別シナリオ群)]
                 │
                 ▼ (M1: ContextExtractor) 【抽出: 厳密因果スライス】
  [RawContextModel (シナリオ垂直事実モデル)]
                 │
                 ▼ (M2: FormalTranspiler) 【昇華: 形式モデル変換】
  ┌────────────────────────────────────────────────────────┐
  │ ★【唯一の永続化正本】 形式仕様コード (`FormalSpec`)   │
  └────────────────────────┬───────────────────────────────┘
                           │ (定常ループへ移行)
                           ▼
【フェーズ B: 定常運用サイクル (Steady-State Autonomous Loop)】
  ┌────────────────────────────────────────────────────────┐
  │ 【唯一の永続化正本】 形式仕様コード (`FormalSpec`)    │
  └──────────────┬───────────────────┬─────────────────────┘
                 │ (M3: FormalSolver)│ (M5: SpecProjector)
                 ▼ 【数学的証明】    ▼ 【多面的射影】
  [SolverReport (反例トレース)]      [SpecificationViews]
                 │                   ・Markdown仕様書 (spec.md)
                 ▼ (M4: LedgerSynthesizer) ・Mermaidシーケンス図 / DAG
  [DomainLedgerCatalog (意思決定論点)]     ・テスト仕様書 / アンカーテスト
                 │ 【畳む: 知識還元】
                 ▼
  [人間 (PdM) による合意・コミット] ➔ [親コンテキスト文脈へマージ]
```

### 3.2 Loom 3大操作によるライフサイクル統制

1. **置く（分解 / Decompose）**:
   - `M0 ScenarioExtractor` がシステム全体から Bounded Context（プロジェクト）を同定し、個別シナリオ（タスク）をアトミックに切り出す。
   - `M1 ContextExtractor` が各個別シナリオの境界（Inlet ➔ Outlet）のみをピンポイントで抽出し、`M2 FormalTranspiler` が形式仕様コードへコンパイルする。
2. **畳む（集約 / Fold）**:
   - `M3 FormalSolver` が全探索した反例を `M4 LedgerSynthesizer` が根本論点へとトポロジカル集約する。
   - 人間が合意した意思決定結果（Domain Ledger）を、親コンテキストの「文脈（全体イベントストリーム・仕様正本）」へと折りたたむ。
3. **移す（伝播 / Transfer）**:
   - あるコンテキストのシナリオ完了で確定したドメインイベントを、別コンテキストのポリシー起動トリガーへと越境伝播させる。
   - コンテキスト間は直接コード参照を持たず、Event Storming Map 上の共有イベント定義のみを介して疎結合に結合する。

## 4. 大域的不変条件と契約仕様 (Global Invariants & Contracts)

### 4.1 大域的事前条件 (Global Preconditions)
1. **原本の非破壊性**: 入力されるソースコードおよび画面画像は Read-only として参照され、システムはこれを直接改変しない。
2. **正本の単一性**: 仕様の正本は形式仕様言語で記述されたコードただ 1 系統のみであり、他のすべてのドキュメント（Markdown/図）はそこからのオンデマンド射影であること。

### 4.2 大域的事後条件 (Global Postconditions)
1. **数学的健全性 (Soundness)**: ソルバによって**指定スコープ内で**検出されたすべての不変条件違反・未定義遷移は、漏れなく元の記録（`SolverReport`）に残り、そこからたどれる形で人間に提示されること。
   - `SolverReport` は**元の記録**であり、全件と実行条件（Alloy の版、SAT ソルバ、スコープ、分割の仕方）を保持する。「漏れなく」の約束はここに課す。
   - `DomainLedgerCatalog` は**要約（コピー）**であり、根本論点を優先してまとめてよい。その代わり、どの `SolverReport` の反例 N 件を論点 k 件にまとめたか、および従属として後ろに回した反例がどれかを必ず記録する（Loom で文脈を畳むときに「… まで／N 件」を書くのと同じ流儀）。
   - 形式仕様正本が更新されると、それより前の `SolverReport` から作った `DomainLedgerCatalog` は古くなる。古いことが分かる印を付け、再検証を促す。
2. **完全隠蔽性**: 生成される仕様書、図式、論点カタログ、および形式仕様正本の公開識別子には、内部実装依存の言語予約語や内部変数が1文字も漏洩しないこと。原本との対応を示す出どころ注釈（`@source` など）は正本の中に保持してよいが、射影と論点カタログでは必ず取り除く。

### 4.3 大域的不変条件 (Global Invariants)
1. **完全決定論性の不変条件 (Determinism Invariant)**:
   同一の形式仕様正本からは、1秒後でも1年後でも、出力される仕様書 Markdown および図式テキストはバイト単位で 100% 完全一致しなければならない。
   - これは決定論的な処理（射影など）に対する約束である。LLM を使う処理は、出力を記録して再利用することで一致させる。担当の一覧は `system_solution.design.md` の 1.2 にある。
2. **決定事項の不破壊性 (Preservation of Accepted Invariants)**:
   人間が一度承認・コミットしたドメイン不変条件（Domain Ledger における合意結果）は、下流のコード変更や再生成によって自動上書き・削除されてはならない。

## 5. 実行基盤およびインフラ方針 (Runtime & Infrastructure Policy)

1. **言語・ビルド方針**:
   - **開発言語**: **TypeScript (`.ts`)**。厳格な静的型チェックと契約インターフェースを保持。
   - **ビルド・実行**: `tsc` / バンドラーにより、ターゲット **ES2022+ の純粋な JavaScript (`.js`, Pure ESM)** へコンパイルして `dist/` へ出力。ブラウザ（Itera OS / Web Worker）および Headless CLI（Node.js / CI）の双方で無修正動作する。
2. **ソルバエンジン**:
   - **検証エンジンは Alloy 6 の 1 系統に限る**。実行環境ごとに別のエンジンを使い分けない（同じ仕様の検証結果が環境によって変わると、移植性に反するため）。
   - エンジンは外部プロセスとして実行し、コアは `SolverPort` を介して呼び出す。アダプターは、Itera OS からローカルブリッジ経由で手元のマシンの Alloy 6 を起動するものと、CI / Node.js から `java` で直接起動するものの 2 つとする。
   - Alloy から SAT への変換部を自前で持ち、WebAssembly 版などの同じ SAT ソルバをどの環境でも使う構成は、将来の選択肢として残す（処理能力の低いマシンで WebAssembly の実行が難しい場合があるため、現時点では作らない）。
3. **データ永続化**:
   - 形式仕様言語コードを唯一の仕様正本として永続化する。
